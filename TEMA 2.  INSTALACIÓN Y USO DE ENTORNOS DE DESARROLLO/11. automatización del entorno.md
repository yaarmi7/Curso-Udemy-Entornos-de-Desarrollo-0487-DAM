# 4. Automatización del entorno

Un entorno de desarrollo bien configurado no solo permite escribir código: también se encarga de las tareas repetitivas
por el desarrollador. Escribir siempre las mismas estructuras, dar formato al código a mano, compilar con comandos largos
o revisar a ojo si se cumple el estilo del equipo son tareas que consumen tiempo y generan errores.

La **automatización del entorno** consiste en configurar el IDE para que realice estas tareas de forma automática o con
un solo atajo de teclado. El resultado es un trabajo más rápido, un código más uniforme y menos errores antes incluso de
ejecutar el programa.

En este apartado se estudian las cuatro herramientas de automatización más importantes: **snippets, tareas, linters y
formateadores**, además de la personalización general del IDE y la configuración de sus actualizaciones.

## 4.1. ¿Qué es automatizar un entorno de desarrollo?

Automatizar el entorno significa **delegar en el IDE aquellas acciones repetitivas y mecánicas** para que el
desarrollador pueda centrarse en la lógica del programa.

Las ventajas principales son:

- Ahorro de tiempo en tareas repetitivas.
- Reducción de errores humanos.
- Estilo de código uniforme en todo el equipo.
- Detección temprana de fallos.
- Flujo de trabajo más rápido y reproducible.

| Herramienta         | Qué automatiza                                  |
| ------------------- | ----------------------------------------------- |
| **Snippets**        | Escritura de estructuras de código repetidas    |
| **Tareas**          | Compilación, ejecución y empaquetado            |
| **Linters**         | Detección de errores y malas prácticas          |
| **Formateadores**   | Indentación, espacios y estilo del código       |
| **Atajos y ajustes**| Acciones frecuentes y comportamiento del editor |

## 4.2. Snippets (fragmentos de código)

Un **snippet** es una plantilla de código reutilizable que se inserta escribiendo una palabra corta (*prefijo*) y
pulsando una tecla (normalmente `Tab` o `Enter`).

**Ejemplo clásico en Java:** al escribir `sout` y pulsar `Tab`, el IDE sustituye el prefijo por
`System.out.println();`.

### Snippets que incluyen los IDEs

| IDE           | Nombre de la función | Ejemplo de prefijo            |
| ------------- | -------------------- | ----------------------------- |
| VS Code       | Snippets             | `for`, `log` (según lenguaje) |
| IntelliJ IDEA | Live Templates       | `sout`, `psvm`, `fori`        |
| Eclipse       | Templates            | `sysout`, `main`, `for`       |
| NetBeans      | Code Templates       | `sout`, `psvm`, `fori`        |

### Crear un snippet propio en VS Code

Se accede desde `File` → `Preferences` → `Configure Snippets` (o *Configure User Snippets*) y se elige el lenguaje.
El snippet se define en un archivo JSON:

```json
{
  "Imprimir por consola": {
    "prefix": "sout",
    "body": [
      "System.out.println(\"$1\");",
      "$0"
    ],
    "description": "Imprime un mensaje por consola"
  }
}
```

- `prefix`: palabra que activa el snippet.
- `body`: código que se insertará (cada elemento es una línea).
- `$1`, `$2`…: posiciones del cursor al pulsar `Tab` sucesivamente.
- `$0`: posición final del cursor.
- `description`: texto que aparece en la lista de sugerencias.

### Crear una plantilla propia en IntelliJ IDEA

`File` → `Settings` → `Editor` → `Live Templates`. Se elige un grupo, se pulsa **+**, se escribe la abreviatura
(*Abbreviation*), el código de la plantilla y el contexto donde se aplica (por ejemplo, *Java*).

## 4.3. Tareas automatizadas

Una **tarea** es una acción que el IDE ejecuta por nosotros, como compilar, ejecutar un script o empaquetar el
proyecto. En lugar de escribir cada vez el comando en la terminal, se define una vez y se lanza con un atajo.

### Tareas en VS Code (`tasks.json`)

Se crean con `Terminal` → `Configure Tasks`. Se guardan en el archivo `.vscode/tasks.json`:

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Compilar C",
      "type": "shell",
      "command": "gcc main.c -o main",
      "group": {
        "kind": "build",
        "isDefault": true
      },
      "problemMatcher": ["$gcc"]
    }
  ]
}
```

Con `Ctrl + Shift + B` se ejecuta la tarea de *build* predeterminada.

### Tareas en otros IDEs

- **IntelliJ IDEA:** *Run/Debug Configurations* y herramientas de build (Maven, Gradle).
- **Eclipse:** *Run Configurations*, *External Tools* y builders del proyecto.
- **NetBeans:** acciones del proyecto (*Build*, *Clean and Build*) y scripts Ant, Maven o Gradle.

### Sistemas de construcción (build)

Los proyectos grandes automatizan la compilación con herramientas externas que el IDE integra:

| Herramienta  | Lenguaje habitual | Archivo de configuración |
| ------------ | ----------------- | ------------------------ |
| **Maven**    | Java              | `pom.xml`                |
| **Gradle**   | Java / Kotlin     | `build.gradle`           |
| **npm**      | JavaScript        | `package.json`           |
| **Make**     | C / C++           | `Makefile`               |

## 4.4. Linters

Un **linter** es una herramienta de **análisis estático** que revisa el código fuente **sin ejecutarlo** y avisa de
errores potenciales, variables sin usar, malas prácticas o incumplimientos del estilo.

El IDE muestra los avisos directamente en el editor, normalmente con subrayados de colores:

- **Rojo:** error.
- **Amarillo / naranja:** advertencia.
- **Azul / gris:** sugerencia.

### Linters más habituales

| Lenguaje              | Linter                         |
| --------------------- | ------------------------------ |
| JavaScript/TypeScript | **ESLint**                     |
| Python                | **Pylint**, **Flake8**         |
| Java                  | **Checkstyle**, **SonarLint**  |
| C / C++               | **clang-tidy**, **cppcheck**   |

### Ejemplo de problemas que detecta un linter

```python
import os          # Aviso: importación sin usar

def calcular(a,b): # Aviso: falta espacio tras la coma
    resultado = a + b
    return a       # Aviso: la variable 'resultado' se asigna pero no se usa
```

En VS Code se instalan como extensiones (por ejemplo, **ESLint** o **Pylint**). En IntelliJ, Eclipse y NetBeans
muchos análisis vienen integrados o se añaden mediante plugins (SonarLint, Checkstyle).

## 4.5. Formateadores de código

Un **formateador** reorganiza automáticamente el código para que siga un estilo uniforme: indentación, espacios, saltos
de línea, posición de llaves, etc. A diferencia del linter, **no busca errores: cambia el aspecto del código**.

### Formateadores más habituales

| Lenguaje              | Formateador                 |
| --------------------- | --------------------------- |
| JavaScript/TypeScript | **Prettier**                |
| Python                | **Black**                   |
| Java                  | **google-java-format**      |
| C / C++               | **clang-format**            |

### Formatear desde el IDE

| IDE           | Atajo habitual (Windows/Linux)  | Menú                                |
| ------------- | ------------------------------- | ----------------------------------- |
| VS Code       | `Shift + Alt + F`               | `Format Document`                   |
| IntelliJ IDEA | `Ctrl + Alt + L`                | `Code` → `Reformat Code`            |
| Eclipse       | `Ctrl + Shift + F`              | `Source` → `Format`                 |
| NetBeans      | `Alt + Shift + F`               | `Source` → `Format`                 |

### Diferencia entre linter y formateador

| Aspecto             | Linter                        | Formateador                 |
| ------------------- | ----------------------------- | --------------------------- |
| Objetivo            | Detectar problemas            | Unificar el estilo          |
| ¿Modifica el código?| No (solo avisa)               | Sí (reescribe el formato)   |
| Ejemplo             | ESLint, Pylint                | Prettier, Black             |

## 4.6. Personalización y ajustes automáticos

Además de las herramientas anteriores, los IDEs permiten configurar su comportamiento general.

### Formatear al guardar en VS Code (`settings.json`)

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.tabSize": 4,
  "files.autoSave": "afterDelay"
}
```

- `editor.formatOnSave`: da formato al archivo cada vez que se guarda.
- `editor.defaultFormatter`: formateador que se utilizará por defecto.
- `editor.tabSize`: número de espacios por tabulación.
- `files.autoSave`: guarda los cambios automáticamente tras un breve tiempo.

### Acciones al guardar en otros IDEs

- **IntelliJ IDEA:** `Settings` → `Tools` → `Actions on Save` (reformatear código, optimizar *imports*).
- **Eclipse:** `Window` → `Preferences` → `Java` → `Editor` → `Save Actions`.
- **NetBeans:** `Tools` → `Options` → `Editor` → `On Save`.

### Otras personalizaciones frecuentes

- Temas de color y tipografía.
- Atajos de teclado propios (*Keyboard Shortcuts*).
- Diseño de paneles y barras de herramientas.
- Perfiles de configuración por lenguaje o proyecto.
- Sincronización de ajustes entre equipos (*Settings Sync* en VS Code).

## 4.7. Actualización del entorno de desarrollo

Mantener actualizado el IDE es parte de su configuración. Las actualizaciones corrigen errores, mejoran el rendimiento
y solucionan problemas de seguridad.

| IDE           | Cómo comprobar o configurar las actualizaciones            |
| ------------- | ---------------------------------------------------------- |
| VS Code       | Ajuste `update.mode` (`default`, `manual`, `start`, `none`) |
| IntelliJ IDEA | `Help` → `Check for Updates` o *JetBrains Toolbox*         |
| Eclipse       | `Help` → `Check for Updates`                               |
| NetBeans      | `Help` → `Check for Updates`                               |

**Buenas prácticas:**

- Actualizar con regularidad, pero no justo antes de una entrega importante.
- Leer las notas de versión cuando el cambio sea grande.
- Mantener sincronizadas las versiones del IDE, del JDK/intérprete y de las extensiones.

## 4.8. Buenas prácticas de automatización

- Automatizar solo lo que se repite con frecuencia.
- Compartir la configuración del proyecto con el equipo (`.vscode/`, `.editorconfig`, configuración de linter).
- Evitar que el linter y el formateador entren en conflicto: usar reglas compatibles.
- Documentar las tareas y atajos personalizados.
- Revisar periódicamente qué automatizaciones siguen siendo útiles.

## Resumen

| Concepto          | Idea clave                                                    |
| ----------------- | ------------------------------------------------------------- |
| **Snippet**       | Plantilla que inserta código al escribir un prefijo           |
| **Tarea**         | Acción (compilar, ejecutar) lanzada con un atajo              |
| **Linter**        | Analiza el código sin ejecutarlo y avisa de problemas         |
| **Formateador**   | Reorganiza el código para unificar el estilo                  |
| **Actualización** | Mantener el IDE seguro, estable y con las últimas mejoras     |
