# 3. Pruebas de código

Ya se sabe qué es una prueba y qué tipos existen. La pregunta práctica es: **¿qué casos concretos hay que probar?**
Como las pruebas exhaustivas son imposibles, hay que **elegir pocos casos que sean muy buenos**. Para eso existen
técnicas de diseño de casos de prueba.

En este apartado se estudian las técnicas de **caja blanca** (basadas en el código) y de **caja negra** (basadas en la
especificación), con ejemplos en Java.

## 3.1. Las dos grandes familias de técnicas

| Familia         | Se basa en…              | Técnicas principales                                                        |
| --------------- | ------------------------ | --------------------------------------------------------------------------- |
| **Caja blanca** | El código fuente         | Cobertura de sentencias, decisiones, condiciones y caminos; complejidad ciclomática |
| **Caja negra**  | La especificación        | Clases de equivalencia, valores límite, tablas de decisión, conjetura de errores |

Ninguna sustituye a la otra: se utilizan **juntas**.

## 3.2. Código de ejemplo

Para los ejemplos de este apartado se usan dos métodos de Java.

**Método 1: clasificar una edad**

```java
public static String categoria(int edad) {
    if (edad < 0 || edad > 120) {
        throw new IllegalArgumentException("Edad no válida: " + edad);
    }
    if (edad < 12) {
        return "INFANTIL";
    }
    if (edad < 65) {
        return "ADULTO";
    }
    return "JUBILADO";
}
```

Especificación: válidas de 0 a 120; de 0 a 11 → INFANTIL; de 12 a 64 → ADULTO; de 65 a 120 → JUBILADO.

**Método 2: retirar dinero**

```java
public void retirar(double cantidad) {
    if (cantidad <= 0) {
        throw new IllegalArgumentException("Cantidad no válida");
    }
    if (cantidad > saldo) {
        throw new IllegalStateException("Saldo insuficiente");
    }
    saldo -= cantidad;
}
```

## 3.3. Pruebas de caja blanca: cobertura

La **cobertura** (*coverage*) mide **qué porcentaje del código se ha ejecutado** al lanzar un conjunto de pruebas.

| Criterio de cobertura         | Qué exige                                                            |
| ----------------------------- | -------------------------------------------------------------------- |
| **Sentencias** (*statement*)  | Ejecutar cada sentencia al menos una vez                             |
| **Decisiones** (*branch*)     | Que cada decisión (`if`, `while`…) sea verdadera y falsa al menos una vez |
| **Condiciones**               | Que cada condición simple dentro de una decisión sea verdadera y falsa |
| **Caminos** (*path*)          | Recorrer todos los caminos posibles del código                       |

Fórmulas:

```
Cobertura de sentencias = sentencias ejecutadas / sentencias totales × 100
Cobertura de decisiones = resultados de decisión recorridos / resultados posibles × 100
```

### Ejemplo con `categoria`

Las sentencias "de acción" del método son: `throw`, `return "INFANTIL"`, `return "ADULTO"` y `return "JUBILADO"`.

| Conjunto de pruebas       | Sentencias ejecutadas        | Cobertura de sentencias |
| ------------------------- | ---------------------------- | ----------------------- |
| `{30}`                    | `return "ADULTO"`            | 1/4 = 25%               |
| `{30, 5}`                 | ADULTO e INFANTIL            | 2/4 = 50%               |
| `{30, 5, 70}`             | ADULTO, INFANTIL y JUBILADO  | 3/4 = 75%               |
| `{30, 5, 70, -1}`         | Las cuatro                   | 4/4 = **100%**          |

### Diferencia entre cobertura de sentencias y de decisiones

```java
if (x > 0) {
    y = 1;
}
```

Con `x = 5` se ejecutan **todas las sentencias** (100% de sentencias), pero la decisión solo ha sido **verdadera**
(50% de decisiones). Falta un caso con `x <= 0` para ver el otro resultado. Por eso la cobertura de decisiones es **más
exigente** que la de sentencias.

### Ejemplo con `retirar`

| Caso (saldo = 100)  | D1: `cantidad <= 0` | D2: `cantidad > saldo` | Camino recorrido                 |
| ------------------- | ------------------- | ---------------------- | -------------------------------- |
| `retirar(0)`        | Verdadera           | —                      | Lanza `IllegalArgumentException` |
| `retirar(150)`      | Falsa               | Verdadera              | Lanza `IllegalStateException`    |
| `retirar(30)`       | Falsa               | Falsa                  | Resta el saldo                   |

Estos tres casos logran un **100% de cobertura de decisiones**.

### Una advertencia importante

> Una cobertura alta **no garantiza que no haya defectos**. Indica qué código se ha ejecutado, no si los resultados
> se han comprobado bien. Una cobertura baja, en cambio, sí señala con seguridad código que **nadie ha probado**.

## 3.4. Complejidad ciclomática

La **complejidad ciclomática** V(G) mide **cuántos caminos independientes** tiene un método. Sirve para saber cuántos
casos de prueba como mínimo hacen falta para recorrerlos todos.

Fórmulas equivalentes (con un grafo de flujo de aristas A y nodos N):

```
V(G) = A − N + 2
V(G) = número de decisiones simples + 1
```

Se cuenta **cada condición simple** de un `if`, `while`, `for`, `case`… y los operadores `&&` y `||` cuentan como una
condición adicional.

### Ejemplos

| Método           | Decisiones simples                                        | V(G)    |
| ---------------- | --------------------------------------------------------- | ------- |
| `retirar`        | `cantidad <= 0`, `cantidad > saldo`                       | 2 + 1 = **3** |
| `categoria`      | `edad < 0`, `edad > 120`, `edad < 12`, `edad < 65`        | 4 + 1 = **5** |

### Interpretación

| V(G)       | Riesgo del método                             |
| ---------- | --------------------------------------------- |
| 1 – 10     | Sencillo y fácil de probar                    |
| 11 – 20    | Complejidad moderada                          |
| Más de 20  | Muy complejo: difícil de probar y mantener    |

Si un método tiene V(G) = 5, hacen falta **al menos 5 casos** para recorrer todos sus caminos independientes. Un V(G)
alto es una señal para **refactorizar**: dividir el método en otros más pequeños.

## 3.5. Pruebas de caja negra: clases de equivalencia

La técnica de las **clases de equivalencia** agrupa los valores de entrada en **conjuntos que el programa trata de la
misma manera**. Si un valor de la clase funciona, se asume que el resto también; por eso basta con **probar un
representante por clase**.

### Pasos

1. Identificar las condiciones de entrada en la especificación.
2. Dividir en **clases válidas** (entradas aceptadas) y **clases no válidas** (entradas rechazadas).
3. Elegir **un valor representativo** de cada clase.

### Ejemplo con `categoria`

| Clase  | Intervalo        | Tipo         | Resultado esperado | Representante |
| ------ | ---------------- | ------------ | ------------------ | ------------- |
| CE-1   | edad < 0         | No válida    | Excepción          | -5            |
| CE-2   | 0 ≤ edad ≤ 11    | Válida       | INFANTIL           | 6             |
| CE-3   | 12 ≤ edad ≤ 64   | Válida       | ADULTO             | 30            |
| CE-4   | 65 ≤ edad ≤ 120  | Válida       | JUBILADO           | 80            |
| CE-5   | edad > 120       | No válida    | Excepción          | 150           |

Con **5 casos** (uno por clase) se cubren todos los comportamientos distintos del método, en lugar de probar las 122
edades posibles.

## 3.6. Análisis de valores límite

La experiencia demuestra que **los errores se concentran en los bordes** de las clases: confundir `<` con `<=` es uno de
los fallos más habituales. El **análisis de valores límite** complementa las clases de equivalencia probando los valores
**justo en el borde y a ambos lados**.

### Regla práctica

Para cada límite se prueban el valor **inmediatamente anterior**, el **propio límite** y el **inmediatamente
posterior** (o los dos valores a cada lado del borde).

### Ejemplo con `categoria`

| Límite                          | Valores a probar | Resultado esperado                 |
| ------------------------------- | ---------------- | ---------------------------------- |
| Entre no válida y INFANTIL      | -1, 0            | Excepción, INFANTIL                |
| Entre INFANTIL y ADULTO         | 11, 12           | INFANTIL, ADULTO                   |
| Entre ADULTO y JUBILADO         | 64, 65           | ADULTO, JUBILADO                   |
| Entre JUBILADO y no válida      | 120, 121         | JUBILADO, Excepción                |

En total 8 valores: **-1, 0, 11, 12, 64, 65, 120, 121**. Una implementación con `edad <= 12` en lugar de `edad < 12`
pasaría las pruebas de las clases de equivalencia (valores 6 y 30) pero **fallaría con el 12**. Por eso se usan las dos
técnicas juntas.

### Ejemplo con valores decimales

Para una nota de 0 a 10 con aprobado en 5, los valores límite son: `-0.01, 0, 4.99, 5, 10, 10.01`.

## 3.7. Conjetura de errores

La **conjetura de errores** (*error guessing*) consiste en usar la **experiencia** para imaginar qué entradas suelen
romper un programa, aunque la especificación no las mencione.

Valores típicos para sospechar:

| Tipo de dato   | Valores problemáticos                                                  |
| -------------- | ---------------------------------------------------------------------- |
| Números        | 0, negativos, el máximo y mínimo del tipo, `Double.NaN`, infinito      |
| Textos         | Cadena vacía, `null`, espacios, caracteres especiales, texto muy largo |
| Colecciones    | Vacía, con un solo elemento, con `null`                                |
| Decimales      | Errores de redondeo (por ejemplo, `0.1 + 0.2` no es exactamente `0.3`) |

### Ejemplo con `CuentaBancaria.ingresar`

El código comprueba `if (cantidad <= 0)`. Pero con `Double.NaN` la comparación `NaN <= 0` **es falsa**, así que el
valor "pasa" la validación y el saldo acaba siendo `NaN`. Ninguna clase de equivalencia ni valor límite lo habría
revelado; **lo descubre la experiencia**.

## 3.8. Tablas de decisión

Cuando el resultado depende de **varias condiciones combinadas**, una **tabla de decisión** recoge todas las
combinaciones y su resultado esperado.

| Condición                     | R1 | R2 | R3 | R4 |
| ----------------------------- | -- | -- | -- | -- |
| ¿Cliente VIP?                 | Sí | Sí | No | No |
| ¿Compra superior a 100 €?     | Sí | No | Sí | No |
| **Descuento aplicado**        | 20% | 10% | 5% | 0% |

Cada columna es una **regla** y da lugar a **un caso de prueba**.

## 3.9. Cómo combinar las técnicas

Un procedimiento razonable para diseñar pruebas de un método:

1. Leer la **especificación** y escribir las **clases de equivalencia**.
2. Añadir los **valores límite** de cada clase.
3. Añadir casos por **conjetura de errores**.
4. Ejecutar y medir la **cobertura** para descubrir código que ninguna prueba ha alcanzado.
5. Añadir casos para las partes sin cubrir.
6. Calcular la **complejidad ciclomática** para saber cuántos casos como mínimo hacen falta.

## Resumen

| Técnica                    | Familia      | Idea clave                                                          |
| -------------------------- | ------------ | ------------------------------------------------------------------- |
| **Cobertura**              | Caja blanca  | Porcentaje de código ejecutado: sentencias, decisiones, condiciones, caminos |
| **Complejidad ciclomática**| Caja blanca  | Nº de caminos independientes = decisiones simples + 1               |
| **Clases de equivalencia** | Caja negra   | Un representante por cada grupo de entradas equivalentes            |
| **Valores límite**         | Caja negra   | Probar en los bordes de las clases, donde se concentran los errores |
| **Conjetura de errores**   | Caja negra   | Usar la experiencia para probar entradas "traviesas"                |
| **Tablas de decisión**     | Caja negra   | Una regla por cada combinación de condiciones                       |
