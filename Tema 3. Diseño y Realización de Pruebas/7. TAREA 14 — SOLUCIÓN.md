## 2. Prueba estructural (caja blanca) (2,00 puntos)

### Ramas del método `retirar` (versión original)

```java
public void retirar(double cantidad) {
    if (cantidad <= 0) {                       // Decisión D1
        throw new IllegalArgumentException("...");   // Rama R1
    }
    if (cantidad >= saldo) {                   // Decisión D2
        throw new IllegalStateException("..."); // Rama R2
    }
    saldo -= cantidad;                          // Rama R3
}
```

| Decisión | Resultado verdadero            | Resultado falso                  |
| -------- | ------------------------------ | -------------------------------- |
| **D1**   | R1: se lanza `IllegalArgumentException` | Se continúa a D2        |
| **D2**   | R2: se lanza `IllegalStateException`    | R3: se resta el saldo   |

### Código de `PruebaEstructural`

```java
package com.ejemplo.banco;

public class PruebaEstructural {

    static void intentar(String rama, double saldoInicial, double cantidad) {
        CuentaBancaria cuenta = new CuentaBancaria(saldoInicial);
        try {
            cuenta.retirar(cantidad);
            System.out.println(rama + " | retirar(" + cantidad + ") | saldo final=" + cuenta.getSaldo());
        } catch (Exception e) {
            System.out.println(rama + " | retirar(" + cantidad + ") | " + e.getClass().getSimpleName());
        }
    }

    public static void main(String[] args) {
        intentar("R1", 100, 0);     // D1 verdadera
        intentar("R2", 100, 150);   // D1 falsa, D2 verdadera
        intentar("R3", 100, 30);    // D1 falsa, D2 falsa
    }
}
```

### Tabla de ramas y entradas

| Rama | Entrada (saldo, cantidad) | Qué ocurre                           | Orden en el depurador |
| ---- | ------------------------- | ------------------------------------ | --------------------- |
| R1   | (100, 0)                  | Lanza `IllegalArgumentException`     | 1.º                   |
| R2   | (100, 150)                | Lanza `IllegalStateException`        | 2.º                   |
| R3   | (100, 30)                 | Resta: saldo final 70                | 3.º                   |

### Comprobación con el depurador de VS Code

1. Puse puntos de ruptura (clic en el margen izquierdo o `F9`) en las tres líneas: la del `throw` de R1, la del
   `throw` de R2 y `saldo -= cantidad;` (R3).
2. Lancé la depuración con `F5` (o con el botón **Debug** sobre `main`).
3. El depurador se detuvo **primero en R1** (con `cantidad = 0.0` en el panel *Variables*), después con `F5` en **R2**
   (`cantidad = 150.0`, `saldo = 100.0`) y por último en **R3** (`cantidad = 30.0`).
4. Con `F10` avancé línea a línea y con `F11` entré en métodos.

**Conclusión:** tres casos recorren las tres ramas y consiguen la **cobertura de decisiones del 100%**: cada
decisión se ha evaluado como verdadera y como falsa al menos una vez.

**Criterios de corrección:** ramas identificadas correctamente (0,50) · tres entradas que recorren cada rama (0,50) ·
uso del depurador con puntos de ruptura y capturas (0,75) · tabla de ramas y orden (0,25).

## 4. Prueba de rendimiento (1,50 puntos)

`PruebaRendimiento.java`:

```java
package com.ejemplo.banco;

public class PruebaRendimiento {
    public static void main(String[] args) {
        CuentaBancaria cuenta = new CuentaBancaria(0);

        long inicio = System.nanoTime();
        for (int i = 0; i < 1_000_000; i++) {
            cuenta.ingresar(1);
        }
        long fin = System.nanoTime();

        long milisegundos = (fin - inicio) / 1_000_000;
        System.out.println("Saldo final: " + cuenta.getSaldo());
        System.out.println("Tiempo: " + milisegundos + " ms");
    }
}
```

Resultados de tres ejecuciones (**valores orientativos**, dependen del equipo):

| Ejecución | Tiempo (ms) |
| --------- | ----------- |
| 1         | 14          |
| 2         | 9           |
| 3         | 8           |

El saldo final mostrado en todas fue `1000000.0`, lo que además confirma que los ingresos se realizaron correctamente.

**Criterio de aceptación definido:** el millón de ingresos debe tardar **menos de 500 ms**.

**Conclusión:** la prueba se supera con un amplio margen. La primera ejecución suele ser algo más lenta porque la
máquina virtual de Java todavía está optimizando el código (*warm-up*), por eso conviene repetir la medición. Es
importante definir el criterio **antes** de medir: un tiempo sin referencia no permite decir si es bueno o malo.

**Criterios de corrección:** código de medición correcto con `System.nanoTime()` (0,50) · tres mediciones (0,25) ·
criterio de aceptación definido (0,25) · conclusión razonada (0,50).

## 5. Clasificación de situaciones (1,50 puntos)

| Situación                                                              | Tipo de prueba          | Justificación                                                    |
| ---------------------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------- |
| a) `Entrada.categoria(70)` devuelve `"JUBILADO"`                       | **Funcional**           | Comprueba una salida frente a la especificación                  |
| b) Que cada `if` de `retirar` se ejecute al menos una vez              | **Estructural**         | Se diseña mirando el código y busca cubrir sus ramas             |
| c) Volver a ejecutar todos los casos tras corregir un defecto          | **Regresión**           | Comprueba que el cambio no rompe lo que ya funcionaba            |
| d) Pasar el linter o una revisión de código sin ejecutar               | **Estática**            | No se ejecuta el programa                                        |
| e) Comprobar solo que la aplicación arranca                            | **Humo**                | Comprobación mínima antes de pruebas más detalladas              |
| f) Medir cuánto tarda en procesar un millón de operaciones             | **Rendimiento**         | Prueba no funcional sobre la velocidad                           |

## 6. Confirmación, regresión, humo, cordura, alfa y beta (1,50 puntos)

| Tipo           | Qué comprueba                                                          | Cuándo                                     |
| -------------- | ---------------------------------------------------------------------- | ------------------------------------------ |
| **Confirmación** | Que un defecto concreto ya está corregido                            | Justo después de corregirlo                |
| **Regresión**  | Que un cambio no ha roto funcionalidades que ya funcionaban            | Tras cada cambio relevante                 |
| **Humo**       | Que lo más básico funciona (arranca, funciones principales responden)  | Al recibir una versión nueva               |
| **Cordura**    | Que un cambio o corrección concretos tienen sentido, de forma rápida   | Tras una corrección pequeña                |

| Tipo     | Quién                                          | Dónde                          | Objetivo                                        |
| -------- | ---------------------------------------------- | ------------------------------ | ----------------------------------------------- |
| **Alfa** | Usuarios internos o equipo de la propia empresa | Entorno del desarrollador      | Encontrar defectos antes de abrir el producto   |
| **Beta** | Grupo reducido de usuarios externos            | Entorno real del usuario       | Comprobar el comportamiento en condiciones reales |

## Conclusión

Cada tipo de prueba descubre problemas distintos: la funcional encontró el defecto de `Entrada` en el límite de los
12 años, la estructural permitió comprobar que se recorren todas las ramas de `retirar`, la de regresión confirmó la
corrección sin romper nada y la de rendimiento midió si la operación es suficientemente rápida. Combinarlas es lo que
da confianza en el programa.
