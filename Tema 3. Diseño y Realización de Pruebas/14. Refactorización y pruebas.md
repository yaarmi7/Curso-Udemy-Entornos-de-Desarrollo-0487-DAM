# 5. Refactorización y pruebas

El código no se escribe una vez y se olvida: se lee, se modifica y se amplía durante años, a menudo por personas
distintas a quien lo escribió. Un código que "funciona pero nadie entiende" es peligroso, porque cualquier cambio puede
romperlo sin que nadie lo note.

La **refactorización** es la técnica que permite mejorar la estructura del código de forma segura. Y su aliado
imprescindible son **las pruebas**: sin ellas, refactorizar es como cambiar los cimientos de una casa sin saber si se
sostiene. En este apartado se estudia qué es refactorizar, cuándo hacerlo, qué técnicas existen y cómo combinarlas con
las pruebas automáticas en Visual Studio Code.

## 5.1. ¿Qué es refactorizar?

**Refactorizar** es **modificar la estructura interna del código para hacerlo más claro, sencillo y fácil de mantener,
sin cambiar su comportamiento externo**.

La clave está en la última parte: **el programa debe hacer exactamente lo mismo antes y después**.

| Actividad                  | ¿Cambia el comportamiento? | Ejemplo                                                |
| -------------------------- | -------------------------- | ------------------------------------------------------ |
| **Refactorizar**           | No                         | Extraer un método, renombrar una variable              |
| **Corregir un defecto**    | Sí (para bien)             | Cambiar `>=` por `>` en `retirar`                      |
| **Añadir una funcionalidad** | Sí                       | Añadir un nuevo tipo de cliente con descuento          |
| **Optimizar el rendimiento** | Puede mantenerlo pero busca velocidad | Sustituir un algoritmo lento por otro rápido |

Mezclar estas actividades es una fuente de errores. Una buena práctica es **separarlas**: primero refactorizar (con las
pruebas en verde), después añadir funcionalidad, y no hacer las dos cosas a la vez.

## 5.2. ¿Por qué refactorizar?

- El código se vuelve más **legible**, y se lee muchas más veces de las que se escribe.
- Se reduce la **deuda técnica**: los atajos que se tomaron "para salir del paso" y que se pagan después.
- Resulta más fácil **añadir funcionalidades** y **encontrar defectos**.
- Se elimina código **duplicado**, de modo que un cambio se hace en un solo sitio.
- Mejora la **testabilidad**: las piezas pequeñas son más fáciles de probar.

## 5.3. Malos olores del código (*code smells*)

Un **mal olor** es una señal de que el código **podría tener un problema de diseño**. No es un error: el programa
funciona, pero es una invitación a refactorizar.

| Mal olor                          | Descripción                                                       | Ejemplo                                        |
| --------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| **Código duplicado**              | El mismo fragmento aparece en varios sitios                       | Tres `if` casi idénticos                       |
| **Método largo**                  | Un método hace demasiadas cosas                                   | Un método de 80 líneas                         |
| **Clase grande**                  | Una clase con demasiadas responsabilidades                        | Una clase que valida, calcula, guarda y muestra |
| **Números mágicos**               | Valores literales sin explicación                                 | `total * 0.21`                                 |
| **Nombres poco claros**           | Variables o métodos que no explican su propósito                  | `double r`, `int x2`, `proc()`                 |
| **Lista larga de parámetros**     | Métodos con muchos argumentos                                     | `crear(a, b, c, d, e, f, g)`                   |
| **Condicionales complejos**       | Cadenas largas de `if`/`else` o expresiones difíciles de leer     | `if (a && !b \|\| c && d)`                     |
| **Código muerto**                 | Código que nunca se ejecuta                                       | Métodos sin usar, variables sin leer           |
| **Comentarios que explican código confuso** | El comentario compensa lo poco claro del código         | `// suma 1 al contador` sobre `c++`            |

Herramientas ya conocidas ayudan a detectarlos: los **linters** señalan código muerto y variables sin usar, y la
**complejidad ciclomática** alta indica métodos que conviene dividir.

## 5.4. Técnicas de refactorización

| Técnica                          | Qué hace                                                       | Cuándo usarla                                  |
| -------------------------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| **Renombrar**                    | Da un nombre más claro a una variable, método o clase          | Nombres poco descriptivos                      |
| **Extraer método**               | Convierte un fragmento en un método con nombre propio          | Método largo o código duplicado                |
| **Extraer variable**             | Guarda una expresión compleja en una variable con nombre       | Expresiones difíciles de leer                  |
| **Extraer constante**            | Sustituye un número mágico por una constante con nombre        | Valores literales repetidos o sin explicación  |
| **Inline (eliminar intermediario)** | Sustituye un método o variable trivial por su contenido     | Variable o método que no aporta claridad       |
| **Mover método**                 | Cambia un método a la clase a la que realmente pertenece       | Método que usa más datos de otra clase         |
| **Simplificar condicionales**    | Reescribe una condición compleja de forma más clara            | `if` anidados o con varias condiciones         |
| **Eliminar código muerto**       | Borra lo que no se usa                                         | Métodos o variables sin referencias            |

### Ejemplo: antes de refactorizar

```java
public double envio(double p, String z) {
    double r = 0;
    if (z.equals("NACIONAL")) {
        r = 3.5 + p * 0.8;
    } else if (z.equals("EUROPA")) {
        r = 8.0 + p * 1.5;
    }
    if (p > 20) {
        r = r + 5;
    }
    return r;
}
```

Problemas: nombres de una letra (`p`, `z`, `r`), números mágicos (`3.5`, `0.8`, `8.0`, `1.5`, `20`, `5`) y un método que
mezcla varias responsabilidades.

### Ejemplo: después de refactorizar

```java
private static final double BASE_NACIONAL = 3.5;
private static final double POR_KILO_NACIONAL = 0.8;
private static final double BASE_EUROPA = 8.0;
private static final double POR_KILO_EUROPA = 1.5;
private static final double UMBRAL_PESO_ELEVADO = 20;
private static final double RECARGO_PESO_ELEVADO = 5;

public double calcularCosteEnvio(double pesoKg, String zona) {
    return costeBase(pesoKg, zona) + recargoPorPeso(pesoKg);
}

private double costeBase(double pesoKg, String zona) {
    if (zona.equals("NACIONAL")) {
        return BASE_NACIONAL + pesoKg * POR_KILO_NACIONAL;
    }
    if (zona.equals("EUROPA")) {
        return BASE_EUROPA + pesoKg * POR_KILO_EUROPA;
    }
    return 0;
}

private double recargoPorPeso(double pesoKg) {
    return pesoKg > UMBRAL_PESO_ELEVADO ? RECARGO_PESO_ELEVADO : 0;
}
```

El comportamiento es **idéntico**, pero ahora cada pieza tiene un nombre que explica su propósito y cada valor
numérico se entiende.

## 5.5. Refactorización y pruebas: la red de seguridad

La regla de oro de la refactorización es:

> **No se refactoriza sin pruebas que verifiquen que el comportamiento no cambia.**

Un cambio "inocente" de estructura puede alterar el resultado sin que nadie se dé cuenta. Las pruebas automáticas
actúan como **red de seguridad**: si tras un cambio alguna se pone en rojo, se sabe inmediatamente que se ha roto algo.

### Procedimiento seguro

1. Asegurar que existen **pruebas que pasan** (en verde) para el código que se va a modificar.
2. Hacer **un cambio pequeño** de refactorización.
3. **Ejecutar todas las pruebas.**
4. Si siguen en verde, continuar. Si alguna falla, **deshacer** el último cambio y revisarlo.
5. Repetir con el siguiente cambio pequeño.

### Pruebas de caracterización

¿Y si el código no tiene pruebas? Antes de tocarlo se escriben **pruebas de caracterización**: pruebas que **describen
lo que el código hace ahora**, aunque no se sepa si es lo "correcto". Su objetivo no es validar la especificación, sino
**fijar el comportamiento actual** para detectar cualquier cambio durante la refactorización.

## 5.6. Refactorizar en Visual Studio Code

Con el *Extension Pack for Java*, VS Code incluye herramientas de refactorización que modifican el código de forma
segura y actualizan todas las referencias.

| Refactorización             | Cómo se invoca                                                              |
| --------------------------- | --------------------------------------------------------------------------- |
| **Renombrar símbolo**       | `F2` sobre el nombre; actualiza todas las referencias del proyecto          |
| **Extraer a método**        | Seleccionar el código → `Ctrl + .` → *Extract to method*                    |
| **Extraer a constante**     | Seleccionar el valor → `Ctrl + .` → *Extract to constant*                   |
| **Extraer a variable local**| Seleccionar la expresión → `Ctrl + .` → *Extract to local variable*         |
| **Inline**                  | `Ctrl + .` sobre la variable o método → *Inline*                            |
| **Menú de refactorización** | Seleccionar código → `Ctrl + Mayús + R` o clic derecho → *Refactor…*        |
| **Organizar imports**       | `Mayús + Alt + O`                                                           |

Las opciones concretas disponibles pueden variar según la versión de las extensiones. Conviene **ejecutar las pruebas
tras cada refactorización** (botón del Test Explorer o `mvn test`).

## 5.7. Desarrollo guiado por pruebas (TDD)

El **desarrollo guiado por pruebas** (*Test-Driven Development*) invierte el orden habitual: **primero se escribe la
prueba y después el código** que la hace pasar. Se trabaja en ciclos muy cortos:

| Fase         | Color  | Qué se hace                                                          |
| ------------ | ------ | -------------------------------------------------------------------- |
| **Red**      | Rojo   | Escribir una prueba para la nueva funcionalidad y ver que **falla**  |
| **Green**    | Verde  | Escribir **el código mínimo** para que la prueba pase                |
| **Refactor** | Azul   | Mejorar el código con todas las pruebas en verde                     |

```
   ┌────────────┐
   │   RED      │  escribir una prueba que falla
   └─────┬──────┘
         ▼
   ┌────────────┐
   │   GREEN    │  hacerla pasar con el código mínimo
   └─────┬──────┘
         ▼
   ┌────────────┐
   │  REFACTOR  │  mejorar el código con las pruebas en verde
   └─────┬──────┘
         └──────► (vuelta a empezar)
```

### Ventajas del TDD

- Obliga a pensar **qué debe hacer** el código antes de escribirlo.
- Garantiza que cada funcionalidad tiene su prueba.
- Genera código más sencillo y fácil de probar.
- La refactorización está siempre respaldada por pruebas.

### Ejemplo de ciclo

1. **Red:** se escribe `descuentoParaEmpresaEs10Porciento`, que llama a código que aún no existe o devuelve otro valor.
   Se ejecuta y falla.
2. **Green:** se añade el caso `"EMPRESA"` con el 10% al código. La prueba pasa.
3. **Refactor:** se extrae el 10% a una constante y se simplifica el código. Las pruebas siguen en verde.

## 5.8. Cuándo no conviene refactorizar

| Situación                                         | Recomendación                                       |
| ------------------------------------------------- | --------------------------------------------------- |
| No hay pruebas y no se pueden escribir            | Mucho riesgo: primero escribir pruebas de caracterización |
| Justo antes de una entrega crítica                | Esperar: el riesgo supera el beneficio              |
| El código se va a reescribir por completo         | No merece la pena mejorarlo                         |
| Se mezcla con una corrección o una nueva funcionalidad | Separar los cambios en pasos distintos         |

## 5.9. Refactorización y control de versiones

Cada refactorización debería ser **un commit propio**, con un mensaje claro (por ejemplo, *"Refactor: extraer constantes
de IVA y descuentos"*). Así, si algo sale mal, se puede **volver al estado anterior** sin perder el resto del trabajo.
Esto conecta con el último apartado del tema, dedicado a Git.

## Resumen

| Concepto                  | Idea clave                                                                |
| ------------------------- | ------------------------------------------------------------------------- |
| **Refactorizar**          | Mejorar la estructura del código **sin cambiar su comportamiento**        |
| **Mal olor**              | Señal de un posible problema de diseño (duplicación, números mágicos…)    |
| **Técnicas**              | Renombrar, extraer método/variable/constante, inline, simplificar         |
| **Red de seguridad**      | Las pruebas en verde antes, durante y después de cada cambio              |
| **Pruebas de caracterización** | Fijan el comportamiento actual de un código sin pruebas              |
| **TDD**                   | Ciclo Red → Green → Refactor: primero la prueba, después el código        |
| **VS Code**               | `F2` renombrar, `Ctrl + .` extraer, `Ctrl + Mayús + R` menú de refactor   |
