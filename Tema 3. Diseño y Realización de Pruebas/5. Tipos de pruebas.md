# 2. Tipos de pruebas

No existe una única forma de probar un programa. Según **qué se quiere comprobar**, **cuánto se conoce del código** y
**en qué momento** se hace, se utilizan pruebas de distinto tipo. Un buen plan de pruebas combina varias, porque cada
una descubre defectos que las demás no ven.

En este apartado se estudian los principales tipos de pruebas, cómo se clasifican y cuándo conviene usar cada uno.

## 2.1. Formas de clasificar las pruebas

Las pruebas pueden clasificarse desde varios puntos de vista, que no se excluyen entre sí:

| Criterio de clasificación        | Tipos                                                          |
| -------------------------------- | -------------------------------------------------------------- |
| **Por el objetivo**              | Funcionales, no funcionales, estructurales, de cambios         |
| **Por el conocimiento del código** | Caja negra, caja blanca, caja gris                          |
| **Por la ejecución del código**  | Estáticas y dinámicas                                          |
| **Por el nivel**                 | Unitarias, de integración, de sistema, de aceptación           |
| **Por quién las ejecuta**        | Manuales y automáticas; alfa y beta                            |

Por ejemplo, una prueba unitaria de `retirar` escrita con JUnit puede ser a la vez **funcional**, de **caja negra**,
**dinámica** y **automática**.

## 2.2. Pruebas funcionales

Las **pruebas funcionales** comprueban que el programa **hace lo que debe hacer** según su especificación. Se fijan en
las entradas y en las salidas, sin importar cómo está escrito el código por dentro.

**Ejemplo:** la especificación dice que se puede retirar todo el saldo de una cuenta. La prueba funcional comprueba que
`retirar(100)` en una cuenta de 100 € deja el saldo en 0.

Preguntas típicas que responde una prueba funcional:

- ¿Devuelve el resultado correcto para entradas válidas?
- ¿Rechaza adecuadamente las entradas no válidas?
- ¿Gestiona bien los casos especiales?

## 2.3. Pruebas no funcionales

Las **pruebas no funcionales** comprueban **cómo** funciona el programa: no solo si da el resultado correcto, sino si lo
hace con la calidad esperada.

| Tipo                       | Qué comprueba                                                      | Ejemplo                                              |
| -------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------- |
| **Rendimiento**            | Rapidez y consumo de recursos                                      | Procesar 1.000.000 de operaciones en menos de un segundo |
| **Carga**                  | Comportamiento con la carga de uso prevista                        | 500 usuarios conectados a la vez                     |
| **Estrés**                 | Comportamiento al superar los límites previstos                    | 10.000 usuarios simultáneos: ¿se recupera después?   |
| **Seguridad**              | Resistencia ante accesos o datos maliciosos                        | Intentar acceder sin autenticación                   |
| **Usabilidad**             | Facilidad de uso                                                   | ¿Encuentra un usuario nuevo cómo hacer una transferencia? |
| **Compatibilidad**         | Funcionamiento en distintos sistemas o versiones                   | Probar en Windows, Linux y distintas versiones de Java |
| **Fiabilidad**             | Capacidad de funcionar sin fallos durante un tiempo                | Ejecutar el servicio 24 horas seguidas               |

### Ejemplo sencillo de prueba de rendimiento en Java

```java
long inicio = System.nanoTime();
CuentaBancaria cuenta = new CuentaBancaria(0);
for (int i = 0; i < 1_000_000; i++) {
    cuenta.ingresar(1);
}
long fin = System.nanoTime();
System.out.println("Tiempo: " + (fin - inicio) / 1_000_000 + " ms");
```

Con `System.nanoTime()` se mide cuánto tarda una operación. La prueba solo es útil si se compara con un **criterio
definido** (por ejemplo, "menos de 500 ms").

## 2.4. Pruebas estructurales

Las **pruebas estructurales** se diseñan **mirando el código** y buscan que se ejecuten sus distintas partes:
sentencias, decisiones, bucles y caminos. Se corresponden con las pruebas de **caja blanca**, que se estudiarán en
detalle en el apartado siguiente.

**Ejemplo:** el método `retirar` tiene tres decisiones posibles (cantidad no positiva, cantidad que supera el saldo y
retirada correcta). Una prueba estructural busca casos que obliguen a ejecutar **cada una**.

## 2.5. Pruebas relacionadas con los cambios

Cuando el código se modifica, hay que comprobar dos cosas: que el cambio arregla lo que debía y que no estropea nada
más.

| Tipo                       | Qué comprueba                                                         | Ejemplo                                                    |
| -------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| **Prueba de confirmación** | Que un defecto concreto se ha corregido                               | Repetir CP-08 tras cambiar `>=` por `>`                    |
| **Prueba de regresión**    | Que los cambios no han roto funcionalidades que ya funcionaban        | Volver a ejecutar todos los casos tras la corrección       |

La **regresión** es la gran razón para automatizar: cada vez que se cambia el código hay que repetir muchas pruebas, y
hacerlo a mano es lento y propenso a olvidos.

> Una corrección puede arreglar un defecto y **crear otro**. Sin pruebas de regresión, nadie se entera hasta que lo
> descubre el usuario.

## 2.6. Pruebas de humo y de cordura

| Tipo                        | Objetivo                                                                  | Cuándo se hace                           |
| --------------------------- | ------------------------------------------------------------------------- | ---------------------------------------- |
| **Prueba de humo (*smoke*)**| Comprobar que lo **más básico** funciona (el programa arranca, compila, las operaciones principales responden) | Al recibir una nueva versión |
| **Prueba de cordura (*sanity*)** | Comprobar de forma rápida que una **corrección o cambio concreto** tiene sentido | Tras una corrección pequeña |

Si la prueba de humo falla, no tiene sentido seguir con pruebas más detalladas: la versión está demasiado rota.

## 2.7. Caja negra, caja blanca y caja gris

| Enfoque         | Conocimiento del código | Se basa en…                      | Qué busca                                          |
| --------------- | ----------------------- | -------------------------------- | -------------------------------------------------- |
| **Caja negra**  | Ninguno                 | La especificación                | Que las salidas sean las esperadas para las entradas |
| **Caja blanca** | Total                   | El código fuente                 | Que se ejecuten todas las partes del código        |
| **Caja gris**   | Parcial                 | Especificación y algo de diseño interno | Casos más inteligentes con conocimiento limitado de la estructura |

### Comparación

| Aspecto            | Caja negra                                  | Caja blanca                                   |
| ------------------ | ------------------------------------------- | --------------------------------------------- |
| Quién la realiza   | Probadores o programadores                  | Programadores                                 |
| Ventaja            | Detecta funciones que faltan o están mal    | Detecta código sin probar o lógica incorrecta |
| Limitación         | No sabe qué partes del código se han ejecutado | No detecta funcionalidades que no se programaron |
| Técnicas típicas   | Clases de equivalencia, valores límite      | Cobertura de sentencias, decisiones y caminos |

Las dos son **complementarias**: la caja negra comprueba que se construyó lo correcto y la caja blanca que se probó todo
lo construido.

## 2.8. Pruebas estáticas y dinámicas

| Tipo                | Se ejecuta el código | Ejemplos                                                        |
| ------------------- | -------------------- | --------------------------------------------------------------- |
| **Estáticas**       | No                   | Revisión de código, inspecciones, análisis con un linter        |
| **Dinámicas**       | Sí                   | Pruebas unitarias, de integración, de sistema                   |

Los linters estudiados en el Tema 2 son una forma de **prueba estática automatizada**: detectan problemas sin ejecutar
el programa. Las pruebas estáticas encuentran defectos muy pronto y a bajo coste; las dinámicas encuentran los que solo
aparecen al ejecutar.

## 2.9. Pruebas alfa y beta

Son pruebas de **aceptación** realizadas con usuarios reales antes de la versión final:

| Tipo      | Quién las hace                          | Dónde                       | Objetivo                                         |
| --------- | --------------------------------------- | --------------------------- | ------------------------------------------------ |
| **Alfa**  | Usuarios internos o equipo de la empresa | En el entorno del desarrollador | Detectar defectos antes de abrir el producto al exterior |
| **Beta**  | Un grupo reducido de usuarios externos   | En su propio entorno        | Ver cómo se comporta el producto en condiciones reales |

## 2.10. ¿Qué tipo de prueba usar?

| Situación                                                        | Tipo de prueba adecuada                   |
| ---------------------------------------------------------------- | ----------------------------------------- |
| Comprobar que un método cumple su especificación                 | Funcional (caja negra), unitaria          |
| Asegurarse de que todas las ramas de un método se ejecutan       | Estructural (caja blanca)                 |
| Verificar que el programa responde bien con muchos usuarios      | No funcional: carga o rendimiento         |
| Tras corregir un defecto, repetir todas las pruebas              | Regresión                                 |
| Comprobar rápidamente que una nueva versión arranca              | Humo                                      |
| Buscar problemas sin ejecutar el código                          | Estática (revisión, linter)               |
| Validar el producto con usuarios reales antes de lanzarlo        | Aceptación (alfa o beta)                  |

## Resumen

| Concepto            | Idea clave                                                                  |
| ------------------- | --------------------------------------------------------------------------- |
| **Funcionales**     | ¿Hace lo que debe? Se basan en la especificación                            |
| **No funcionales**  | ¿Lo hace con la calidad esperada? Rendimiento, carga, seguridad, usabilidad |
| **Estructurales**   | Se basan en el código y buscan ejecutar todas sus partes                    |
| **Regresión**       | Comprueban que un cambio no ha roto lo que ya funcionaba                    |
| **Humo**            | Comprobación rápida de lo más básico                                        |
| **Caja negra / blanca** | Sin conocer el código / conociéndolo; se complementan                   |
| **Estáticas / dinámicas** | Sin ejecutar el código / ejecutándolo                                 |
