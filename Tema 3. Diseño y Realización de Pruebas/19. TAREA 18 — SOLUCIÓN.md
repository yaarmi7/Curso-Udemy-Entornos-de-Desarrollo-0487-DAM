## 4. Provocar y resolver un conflicto (2,00 puntos)

### Preparación de las dos ramas desde el mismo commit

```bash
git switch -c feature/mensajes-claros
# editar el mensaje de ingresar a: "Cantidad a ingresar no válida (debe ser finita y positiva)"
git commit -am "Mejorar mensaje de ingresar no válido"

git switch main
git switch -c feature/mensajes-cortos
# editar el mismo mensaje a: "Ingreso no válido"
git commit -am "Acortar mensaje de ingresar no válido"

git switch main
```

Ambas ramas parten del mismo commit (`e5f6a7b`) y cambian **la misma línea**.

### Primera fusión: sin problemas

```bash
git merge feature/mensajes-claros
```

```
Fast-forward
```

### Segunda fusión: conflicto

```bash
git merge feature/mensajes-cortos
```

```
Auto-merging src/main/java/com/ejemplo/banco/CuentaBancaria.java
CONFLICT (content): Merge conflict in src/main/java/com/ejemplo/banco/CuentaBancaria.java
Automatic merge failed; fix conflicts and then commit the result.
```

### El archivo **antes** de resolver

```java
        if (!Double.isFinite(cantidad) || cantidad <= 0) {
<<<<<<< HEAD
            throw new IllegalArgumentException("Cantidad a ingresar no válida (debe ser finita y positiva)");
=======
            throw new IllegalArgumentException("Ingreso no válido");
>>>>>>> feature/mensajes-cortos
        }
```

- Entre `<<<<<<< HEAD` y `=======` está **mi versión** (la rama `main`, que ya incluía `mensajes-claros`).
- Entre `=======` y `>>>>>>> feature/mensajes-cortos` está la versión **de la rama que se fusiona**.

### Resolución en VS Code

1. En la vista de control de código fuente, el archivo aparece en **Merge Changes** con el icono de conflicto.
2. Al abrirlo, sobre el conflicto aparecen las acciones **Accept Current Change**, **Accept Incoming Change**,
   **Accept Both Changes** y **Compare Changes** (o se puede usar el editor de fusión con *Resolve in Merge Editor*).
3. Elegí *Accept Both Changes* y edité el texto final para dejar una sola línea coherente, eliminando las marcas
   `<<<<<<<`, `=======` y `>>>>>>>`.

### El archivo **después** de resolver

```java
        if (!Double.isFinite(cantidad) || cantidad <= 0) {
            throw new IllegalArgumentException("Ingreso no válido: la cantidad debe ser finita y positiva");
        }
```

### Comprobación y confirmación

```

[INFO] BUILD SUCCESS
```

Ninguna prueba comprueba el texto de este mensaje, así que siguen en verde. Se prepara el archivo y se confirma:


## 5. Las tres áreas de Git, ramas y fusiones (1,50 puntos)

```
 Directorio de trabajo        Área de preparación           Repositorio local
 ┌──────────────────┐  git add  ┌──────────────────┐ git commit ┌──────────────────┐
 │ Archivos que     │ ────────► │ Cambios elegidos │ ─────────► │ Commits          │
 │ se editan        │           │ para el próximo  │            │ guardados en     │
 │                  │ ◄──────── │ commit (staging) │            │ el historial     │
 └──────────────────┘ git restore└──────────────────┘            └──────────────────┘
```

- **`git add`** mueve los cambios elegidos del directorio de trabajo al **área de preparación**. Permite decidir qué
  entra en cada commit.
- **`git commit`** guarda en el repositorio una **instantánea** de lo que hay en el área de preparación, con un
  mensaje, autor, fecha y un identificador único.
- Una **rama** es una **línea de desarrollo independiente** que permite trabajar en un cambio sin afectar al código
  estable.
- Una **fusión** (*merge*) **une los cambios** de una rama con otra. Puede ser de avance rápido o generar un commit de
  fusión; si dos ramas tocan las mismas líneas, aparece un **conflicto** que se resuelve a mano.

## 6. Tipos de VCS, Git y GitHub, `.gitignore` y mensajes de commit (1,50 puntos)

| Tipo             | Cómo funciona                                                         | Ejemplo        |
| ---------------- | --------------------------------------------------------------------- | -------------- |
| **Local**        | El historial se guarda solo en el equipo del usuario                  | RCS            |
| **Centralizado** | Un servidor central guarda el historial y los usuarios se conectan a él | Subversion (SVN) |
| **Distribuido**  | Cada usuario tiene una copia completa del repositorio y su historial  | Git            |

- **Git** es el **programa** de control de versiones que se instala en el equipo. **GitHub** es un **servicio en
  línea** que aloja repositorios Git y añade herramientas de colaboración (*pull requests*, incidencias…).
- **`.gitignore`** indica los archivos que Git debe ignorar: los generados automáticamente (`target/`, `*.class`), los
  específicos del IDE y los que no deben compartirse (claves, contraseñas).

Tres ejemplos de buenos mensajes de commit:

1. `Añadir pruebas JUnit de CuentaBancaria`
2. `Corregir límite de retirar: permitir retirar todo el saldo`
3. `Refactor: extraer constantes de descuentos e IVA en Factura`

## Conclusión

Git convierte el trabajo del tema en un historial ordenado y reversible: cada paso (código, pruebas, corrección,
refactorización) queda guardado con su mensaje, las ramas permiten trabajar con seguridad sin tocar `main`, y las
pruebas automáticas garantizan que solo se fusiona código que funciona.
