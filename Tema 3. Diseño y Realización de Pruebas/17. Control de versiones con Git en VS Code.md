# 6. Control de versiones con Git en VS Code

A lo largo de este tema se han corregido defectos, escrito pruebas y refactorizado código. Cada cambio es una
oportunidad de mejorar el programa, pero también de estropearlo. ¿Cómo se vuelve atrás si una modificación sale mal?
¿Cómo trabajan varias personas sobre el mismo código sin pisarse? ¿Cómo se sabe quién cambió qué y por qué?

La respuesta es el **control de versiones**. En este apartado se estudian sus conceptos básicos y se aprende a usar
**Git**, el sistema más utilizado del mundo, directamente desde **Visual Studio Code**.

## 6.1. ¿Qué es el control de versiones?

Un **sistema de control de versiones** (VCS, *Version Control System*) registra **los cambios que se hacen en los
archivos de un proyecto a lo largo del tiempo**, de forma que se puede consultar el historial, comparar versiones y
volver a un estado anterior.

### Problemas que resuelve

- **Volver atrás** tras un cambio que ha roto el programa.
- **Historial**: quién hizo cada cambio, cuándo y con qué motivo.
- **Trabajo en equipo**: varias personas trabajan en paralelo sin sobrescribirse.
- **Pruebas sin riesgo**: se experimenta en una copia aislada (rama) sin tocar el código estable.
- **Copia de seguridad** del proyecto, sobre todo si hay un repositorio remoto.

### Vocabulario básico

| Término                   | Significado                                                              |
| ------------------------- | ------------------------------------------------------------------------ |
| **Repositorio**           | Carpeta del proyecto con todo su historial de cambios                    |
| **Commit**                | Una "foto" guardada del estado del proyecto, con un mensaje explicativo  |
| **Historial** (*log*)     | Lista de todos los commits                                               |
| **Rama** (*branch*)       | Línea de desarrollo independiente                                        |
| **Fusión** (*merge*)      | Unir los cambios de una rama con otra                                    |
| **Conflicto**             | Situación en la que dos ramas cambian la misma parte y hay que decidir   |
| **Repositorio remoto**    | Copia del repositorio alojada en un servidor (por ejemplo, GitHub)       |
| **Clonar**                | Descargar una copia completa de un repositorio remoto                    |

## 6.2. Tipos de sistemas de control de versiones

| Tipo             | Cómo funciona                                                               | Ejemplos                    |
| ---------------- | --------------------------------------------------------------------------- | --------------------------- |
| **Local**        | El historial se guarda solo en el equipo del usuario                        | RCS                         |
| **Centralizado** | Un servidor central guarda el historial; los usuarios piden y envían cambios| Subversion (SVN), CVS       |
| **Distribuido**  | **Cada usuario tiene una copia completa del repositorio y de su historial** | **Git**, Mercurial          |

### Ventajas de los sistemas distribuidos

- Se puede trabajar y hacer commits **sin conexión**.
- Cada copia es una **copia de seguridad** completa.
- Crear ramas es muy rápido y barato.
- No hay un único punto de fallo.

### Git y GitHub no son lo mismo

| Herramienta       | Qué es                                                                              |
| ----------------- | ----------------------------------------------------------------------------------- |
| **Git**           | El **programa** de control de versiones que se instala y usa en el equipo           |
| **GitHub / GitLab / Bitbucket** | **Servicios en línea** que alojan repositorios Git y añaden colaboración (*pull requests*, incidencias, etc.) |

## 6.3. Conceptos fundamentales de Git

### Las tres áreas de trabajo

```
 Directorio de trabajo        Área de preparación           Repositorio local
  (working directory)         (staging area / index)        (historial de commits)
 ┌──────────────────┐  git add  ┌──────────────────┐ git commit ┌──────────────────┐
 │ Archivos que     │ ────────► │ Cambios elegidos │ ─────────► │ Commits          │
 │ editas           │           │ para el próximo  │            │ guardados        │
 │                  │ ◄──────── │ commit           │            │                  │
 └──────────────────┘ git restore└──────────────────┘            └──────────────────┘
```

El **área de preparación** permite **elegir qué cambios** entran en el próximo commit, de modo que cada commit
contenga un único cambio con sentido.

### Estados de un archivo

| Estado                      | Significado                                                 |
| --------------------------- | ----------------------------------------------------------- |
| **Sin seguimiento** (*untracked*) | Archivo nuevo que Git aún no controla                 |
| **Modificado** (*modified*) | Archivo controlado con cambios sin preparar                 |
| **Preparado** (*staged*)    | Cambios marcados para incluirse en el próximo commit        |
| **Confirmado** (*committed*)| Cambios guardados en el historial                           |

### El commit

Cada **commit** guarda:

- Una instantánea de los archivos preparados.
- Un **identificador único** (un código hexadecimal, o *hash*, como `a3f9c21`).
- El **autor**, la **fecha** y un **mensaje** descriptivo.
- Una referencia al commit **anterior**, formando una cadena (el historial).

`HEAD` es el puntero que indica **en qué commit y rama se está trabajando** en este momento.

## 6.4. Instalación y configuración inicial

1. Instalar Git (desde la web oficial de Git o con el gestor de paquetes del sistema).
2. Comprobar la instalación:

```bash
git --version
```

3. Configurar la identidad, que se asocia a cada commit:

```bash
git config --global user.name "Nombre Apellidos"
git config --global user.email "correo@ejemplo.com"
git config --global init.defaultBranch main
```

La última línea hace que los repositorios nuevos empiecen con una rama llamada `main`.

## 6.5. Flujo de trabajo básico

```bash
git init                         # crea un repositorio en la carpeta actual
git status                       # muestra el estado de los archivos
git add Archivo.java             # prepara un archivo (o git add . para todos)
git commit -m "Mensaje claro"    # guarda los cambios preparados
git log --oneline                # muestra el historial resumido
git diff                         # muestra los cambios sin preparar
```

### El archivo `.gitignore`

Hay archivos que **no deben guardarse** en el repositorio: los generados automáticamente (se pueden volver a crear) o
los específicos de cada equipo. Se indican en un archivo `.gitignore` en la raíz del proyecto. Para un proyecto Java con
Maven en VS Code:

```
# Resultados de compilación
target/
*.class

# Archivos de IDE
.classpath
.project
.settings/
.idea/
*.iml

# Archivos del sistema
.DS_Store
Thumbs.db
```

> Nunca deben subirse al repositorio contraseñas, claves de acceso ni datos personales.

### Buenos mensajes de commit

| Mal mensaje        | Buen mensaje                                                         |
| ------------------ | -------------------------------------------------------------------- |
| `cambios`          | `Corregir límite de retirar: permitir retirar todo el saldo`         |
| `arreglado`        | `Añadir validación de valores no finitos en CuentaBancaria`          |
| `prueba`           | `Añadir pruebas JUnit de CuentaBancaria`                             |

Un buen mensaje es **breve** (menos de unos 70 caracteres en la primera línea), empieza con un **verbo en infinitivo o
imperativo** y explica **qué** se hizo y, si no es evidente, **por qué**. Un commit debe contener **un único cambio
lógico**.

## 6.6. Git en Visual Studio Code

VS Code incluye soporte de Git sin necesidad de instalar extensiones (solo requiere tener Git instalado).

### La vista de control de código fuente

Se abre con el icono de la rama en la barra lateral o con **`Ctrl + Mayús + G`**.

| Elemento                         | Función                                                                   |
| -------------------------------- | ------------------------------------------------------------------------- |
| **Initialize Repository**        | Crea un repositorio Git en la carpeta abierta                             |
| **Lista de cambios**             | Muestra los archivos modificados con una letra: `U` (sin seguimiento), `M` (modificado), `A` (añadido), `D` (borrado) |
| **Botón `+`** junto al archivo   | Prepara el archivo (*stage*)                                              |
| **Botón `−`**                    | Quita el archivo del área de preparación (*unstage*)                      |
| **Botón de deshacer**            | Descarta los cambios del archivo (¡no se pueden recuperar!)               |
| **Cuadro de mensaje + ✓ Commit** | Escribe el mensaje y confirma los cambios preparados (`Ctrl + Enter`)     |
| **Clic en un archivo**           | Abre la vista de **diferencias** (antes y después)                        |
| **Nombre de la rama (barra de estado)** | Muestra la rama actual; al pulsarlo permite cambiar o crear ramas  |
| **Vista *Timeline*** (Explorador) | Muestra el historial de commits del archivo abierto                      |

### Operaciones desde la paleta de comandos (`Ctrl + Mayús + P`)

| Comando                      | Función                                         |
| ---------------------------- | ----------------------------------------------- |
| `Git: Clone`                 | Clonar un repositorio remoto                    |
| `Git: Create Branch...`      | Crear una rama nueva y cambiar a ella           |
| `Git: Checkout to...`        | Cambiar de rama                                 |
| `Git: Merge Branch...`       | Fusionar una rama en la actual                  |
| `Git: Delete Branch...`      | Borrar una rama                                 |
| `Git: Pull` / `Git: Push`    | Descargar / enviar cambios del remoto           |

### Publicar en GitHub

Con el repositorio local creado, el botón **Publish Branch** o **Publish to GitHub** de la vista de control de
código fuente permite crear el repositorio remoto y subir el código tras iniciar sesión en la cuenta de GitHub.

## 6.7. Ramas

Una **rama** es una línea de desarrollo independiente. Permite trabajar en una tarea (una nueva funcionalidad, la
corrección de un defecto) **sin tocar el código estable** hasta que esté terminada y probada.

```
main      ●────●────●─────────────●────●
                    \           /
feature              ●────●────●
```

### Comandos

```bash
git branch                       # lista las ramas
git switch -c feature/nueva      # crea una rama y cambia a ella
git switch main                  # cambia a otra rama
git branch -d feature/nueva      # borra una rama ya fusionada
```

### Convención de nombres

| Prefijo      | Uso                                    | Ejemplo                       |
| ------------ | -------------------------------------- | ----------------------------- |
| `feature/`   | Nueva funcionalidad                    | `feature/descuento-empresa`   |
| `fix/`       | Corrección de un defecto               | `fix/validacion-nan`          |
| `refactor/`  | Reorganización del código              | `refactor/extraer-constantes` |

### Buenas prácticas

- Mantener las ramas **cortas**: cuanto más viven, más difícil es fusionarlas.
- **Ejecutar las pruebas** en la rama antes de fusionarla.
- La rama principal (`main`) debería estar **siempre en verde**.

## 6.8. Fusión de ramas (*merge*)

```bash
git switch main                  # situarse en la rama que recibirá los cambios
git merge feature/nueva          # fusionar la otra rama en la actual
```

| Tipo de fusión       | Cuándo ocurre                                                          | Resultado                               |
| -------------------- | ---------------------------------------------------------------------- | --------------------------------------- |
| **Avance rápido** (*fast-forward*) | `main` no ha cambiado desde que se creó la rama           | `main` simplemente avanza; no hay commit de fusión |
| **Fusión con commit** | Ambas ramas tienen commits nuevos                                     | Git crea un commit de fusión con dos padres |

Para ver el historial con las ramas dibujadas:

```bash
git log --oneline --graph --all
```

## 6.9. Conflictos de fusión

Un **conflicto** aparece cuando **dos ramas han modificado las mismas líneas** de un archivo de forma distinta: Git no
puede decidir cuál es la correcta y pide ayuda al desarrollador.

### Cómo se presenta

Git deja **marcas** en el archivo:

```
<<<<<<< HEAD
        throw new IllegalArgumentException("Cantidad no válida");
=======
        throw new IllegalArgumentException("La cantidad debe ser positiva");
>>>>>>> feature/mensajes
```

| Marca                | Significado                                              |
| -------------------- | -------------------------------------------------------- |
| `<<<<<<< HEAD`       | Inicio de **tu versión** (rama actual)                   |
| `=======`            | Separador                                                |
| `>>>>>>> feature/mensajes` | Fin de la versión de **la rama que se fusiona**    |

### Resolverlo en VS Code

1. En la vista de control de código fuente, los archivos en conflicto aparecen en **Merge Changes**.
2. Al abrir el archivo, sobre cada conflicto aparecen opciones: **Accept Current Change** (la tuya), **Accept
   Incoming Change** (la de la otra rama), **Accept Both Changes** o **Compare Changes**. Las versiones recientes
   también ofrecen un **editor de fusión** de tres paneles (*Resolve in Merge Editor*).
3. Elegir o escribir la versión final y **eliminar las marcas** `<<<<<<<`, `=======` y `>>>>>>>`.
4. **Ejecutar las pruebas** para comprobar que el resultado funciona.
5. Preparar el archivo (`+`) y hacer el **commit** de la fusión.

Si algo sale mal, se puede cancelar la fusión con:

```bash
git merge --abort
```

## 6.10. Repositorios remotos

```bash
git remote add origin https://github.com/usuario/proyecto.git   # asocia un remoto
git push -u origin main          # envía la rama main (y la enlaza con el remoto)
git pull                         # descarga y fusiona los cambios del remoto
git fetch                        # descarga los cambios sin fusionarlos
git clone https://github.com/usuario/proyecto.git              # copia un repositorio remoto
```

En VS Code, el botón **Sync Changes** (en la barra de estado) hace `pull` y `push` en un solo paso.

### Flujo de trabajo con un remoto

1. **Actualizar** (`pull`) antes de empezar a trabajar.
2. Trabajar en una rama, con commits pequeños.
3. **Probar** que todo funciona.
4. **Enviar** (`push`) los cambios.
5. En proyectos de equipo, abrir una **solicitud de incorporación** (*pull request*) para que otros revisen el cambio
   antes de fusionarlo.

## 6.11. Deshacer cambios

| Situación                                         | Comando                          | Efecto                                            |
| ------------------------------------------------- | -------------------------------- | ------------------------------------------------- |
| Descartar cambios sin preparar de un archivo      | `git restore Archivo.java`       | Vuelve a la última versión confirmada             |
| Quitar un archivo del área de preparación         | `git restore --staged Archivo.java` | Conserva los cambios pero no irán al commit    |
| Deshacer un commit ya hecho **sin borrar historia** | `git revert <hash>`            | Crea un commit nuevo que invierte los cambios     |
| Volver a una versión anterior viendo el código    | `git switch --detach <hash>`     | Permite consultar un commit antiguo               |

> `git restore` sobre cambios sin preparar **no se puede deshacer**. Conviene usar `git revert` cuando el commit ya se
> compartió con otras personas.

## 6.12. Control de versiones y pruebas

| Buena práctica                                                  | Motivo                                                        |
| --------------------------------------------------------------- | ------------------------------------------------------------- |
| **Ejecutar las pruebas antes de cada commit**                   | No guardar en el historial código roto                        |
| **Un commit por refactorización**                               | Facilita deshacer un paso concreto                            |
| **Separar corrección, refactorización y nueva funcionalidad**   | El historial explica qué cambió y por qué                     |
| **Corregir defectos en ramas `fix/`**                           | Aísla el arreglo y permite probarlo antes de fusionar         |
| **Mantener `main` siempre en verde**                            | Cualquiera puede partir de ella con garantías                 |

En equipos profesionales, estas comprobaciones se automatizan con **integración continua**: un servidor ejecuta las
pruebas automáticamente cada vez que alguien envía cambios.
