## 4. Depurar y corregir (1,50 puntos)

### Depuración de `ingresarNaNLanzaExcepcion`

1. Puse un punto de ruptura en la línea `if (cantidad <= 0)` de `ingresar`.
2. Pulsé **Debug Test** sobre `ingresarNaNLanzaExcepcion`. El depurador se detuvo en esa línea.
3. En el panel *Variables*: `cantidad = NaN`.
4. En la **Consola de depuración** evalué `cantidad <= 0` y el resultado fue **`false`**.

**Explicación:** cualquier comparación con `NaN` (`<`, `<=`, `>`, `>=`, `==`) es falsa. Como la condición del `if` es
`cantidad <= 0`, el valor `NaN` no se considera "no positivo", **supera la validación** y se suma al saldo. Hay que
comprobar el valor de forma explícita con `Double.isFinite`.

### Punto de ruptura condicional

En `retirar` puse un punto de ruptura y, con clic derecho → *Edit Breakpoint* → *Expression*, la condición
`cantidad == 100`. Al ejecutar todas las pruebas con *Debug*, el depurador **solo se detuvo en
`retirarTodoElSaldo`** (con `cantidad = 100.0`) y no en `retirarRestaLaCantidadDelSaldo` (30) ni en
`retirarMasQueElSaldo...` (150).

### Corrección

```java
public CuentaBancaria(double saldoInicial) {
    if (!Double.isFinite(saldoInicial) || saldoInicial < 0) {
        throw new IllegalArgumentException(
                "El saldo inicial debe ser un número finito y no negativo");
    }
    this.saldo = saldoInicial;
}

public void ingresar(double cantidad) {
    if (!Double.isFinite(cantidad) || cantidad <= 0) {
        throw new IllegalArgumentException(
                "La cantidad a ingresar debe ser un número finito y positivo");
    }
    saldo += cantidad;
}

public void retirar(double cantidad) {
    if (!Double.isFinite(cantidad) || cantidad <= 0) {
        throw new IllegalArgumentException(
                "La cantidad a retirar debe ser un número finito y positivo");
    }
    if (cantidad > saldo) {
        throw new IllegalStateException("Saldo insuficiente");
    }
    saldo -= cantidad;
}
```

## 6. Anotaciones del ciclo de vida (1,50 puntos)

| Anotación     | Función                                                                     |
| ------------- | --------------------------------------------------------------------------- |
| `@BeforeAll`  | Se ejecuta **una vez** antes de todas las pruebas; el método es `static`    |
| `@BeforeEach` | Se ejecuta **antes de cada prueba**; deja el estado preparado y limpio      |
| `@AfterEach`  | Se ejecuta **después de cada prueba**; libera recursos                      |
| `@AfterAll`   | Se ejecuta **una vez** al terminar todas las pruebas; el método es `static` |

Orden de ejecución con `pruebaA` y `pruebaB`:

```
@BeforeAll
    @BeforeEach
        pruebaA
    @AfterEach
    @BeforeEach
        pruebaB
    @AfterEach
@AfterAll
```

El orden entre `pruebaA` y `pruebaB` **no está garantizado ni debe importar**: las pruebas deben ser independientes.
Por eso se usa `@BeforeEach`, que crea un objeto nuevo antes de cada una.

## 7. Arrange-Act-Assert, F.I.R.S.T. y aserciones (1,50 puntos)

- **Arrange-Act-Assert:** cada prueba se estructura en tres fases: preparar los datos (*Arrange*), ejecutar la acción
  que se prueba (*Act*) y comprobar el resultado (*Assert*).
- **F.I.R.S.T.:** pruebas **rápidas**, **independientes**, **repetibles**, **autovalidadas** y escritas **a tiempo**.

| Aserción         | Cuándo se usa                                                                 |
| ---------------- | ----------------------------------------------------------------------------- |
| `assertEquals`   | Para comparar un valor esperado con el obtenido (por ejemplo, el saldo)       |
| `assertTrue`     | Para comprobar que una condición booleana se cumple                           |
| `assertThrows`   | Para comprobar que un código lanza la excepción esperada (y su mensaje)       |

**Tolerancia con `double`:** los números decimales binarios acumulan errores de redondeo (por ejemplo, diez sumas de
`0.1` no dan exactamente `1.0`). Por eso se compara con una tolerancia (`delta`), de modo que valores prácticamente
iguales se consideren correctos.
