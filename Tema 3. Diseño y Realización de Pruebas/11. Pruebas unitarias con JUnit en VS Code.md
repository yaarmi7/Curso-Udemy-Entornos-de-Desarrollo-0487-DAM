# 4. Pruebas unitarias con JUnit en VS Code

Hasta ahora las pruebas se han ejecutado con clases `main` escritas a mano que imprimían `OK` o `FALLO`. Funciona, pero
tiene problemas: hay que revisar la salida con los ojos, un fallo no detiene nada y cada programador monta sus propias
comprobaciones de forma distinta.

Las **pruebas unitarias automatizadas** resuelven esos problemas. En Java el estándar es **JUnit**, y Visual Studio Code
lo integra mediante la extensión **Test Runner for Java**. En este apartado se aprende a escribir, ejecutar, depurar y
medir la cobertura de pruebas unitarias en ese entorno.

## 4.1. ¿Qué es una prueba unitaria?

Una **prueba unitaria** comprueba el funcionamiento de **la unidad de código más pequeña que tiene sentido probar**
(normalmente un método o una clase) **de forma aislada** del resto del programa.

### Ventajas

- Detectan defectos muy pronto, cuando son baratos de corregir.
- Se ejecutan en segundos, así que pueden lanzarse cada vez que se cambia el código.
- Funcionan como **red de seguridad** para refactorizar y modificar sin miedo.
- Documentan con ejemplos cómo debe comportarse el código.
- Indican con precisión **dónde** está el problema.

### Características de una buena prueba unitaria: principios F.I.R.S.T.

| Letra | Principio          | Significado                                                           |
| ----- | ------------------ | --------------------------------------------------------------------- |
| **F** | *Fast* (rápida)    | Se ejecuta en milisegundos                                            |
| **I** | *Independent*      | No depende de otras pruebas ni del orden de ejecución                 |
| **R** | *Repeatable*       | Da el mismo resultado siempre y en cualquier equipo                   |
| **S** | *Self-validating*  | Decide sola si ha pasado o no (sin que una persona lea la salida)     |
| **T** | *Timely* (a tiempo)| Se escribe junto con el código, o incluso antes                       |

## 4.2. ¿Qué es JUnit?

**JUnit** es el framework de pruebas unitarias más utilizado en Java. Su versión actual, **JUnit 5**, se compone de:

| Módulo               | Función                                                              |
| -------------------- | -------------------------------------------------------------------- |
| **JUnit Platform**   | Base que permite lanzar pruebas desde IDEs y herramientas de build   |
| **JUnit Jupiter**    | El modelo de programación y las anotaciones de JUnit 5 (`@Test`…)    |
| **JUnit Vintage**    | Permite ejecutar pruebas escritas con JUnit 3 y 4                    |

En este tema se usa **JUnit Jupiter** (JUnit 5).

## 4.3. Preparar el entorno en Visual Studio Code

### Extensiones necesarias

El **Extension Pack for Java** incluye todo lo necesario:

| Extensión                           | Para qué sirve                                         |
| ----------------------------------- | ------------------------------------------------------ |
| **Language Support for Java (Red Hat)** | Autocompletado, errores y navegación en Java       |
| **Debugger for Java**               | Depuración con puntos de ruptura                       |
| **Test Runner for Java**            | Ejecutar y depurar pruebas JUnit desde el editor       |
| **Maven for Java**                  | Gestionar proyectos Maven                              |
| **Project Manager for Java**        | Organizar proyectos y dependencias                     |

El *Test Runner for Java* admite **JUnit 4 y JUnit 5** (y TestNG).

### El `pom.xml` con JUnit 5

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.ejemplo</groupId>
  <artifactId>pruebas-tema3</artifactId>
  <version>1.0-SNAPSHOT</version>

  <properties>
    <maven.compiler.source>17</maven.compiler.source>
    <maven.compiler.target>17</maven.compiler.target>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <junit.version>5.10.2</junit.version>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>${junit.version}</version>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.2.5</version>
      </plugin>
    </plugins>
  </build>
</project>
```

- La dependencia con `<scope>test</scope>` solo se usa al probar, no entra en el programa final.
- El plugin **Surefire** es el que ejecuta las pruebas al lanzar `mvn test`.
- Las versiones pueden actualizarse a las más recientes publicadas en Maven Central.

### Estructura de carpetas

Maven separa el código de producción del de pruebas:

```
pruebas-tema3/
├── pom.xml
└── src/
    ├── main/java/com/ejemplo/banco/CuentaBancaria.java
    └── test/java/com/ejemplo/banco/CuentaBancariaTest.java
```

La clase de prueba va en **el mismo paquete** que la clase que prueba y se nombra con el sufijo **`Test`**.

## 4.4. Mi primera prueba con JUnit 5

```java
package com.ejemplo.banco;

import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;

class CuentaBancariaTest {

    @Test
    void ingresarSumaLaCantidadAlSaldo() {
        CuentaBancaria cuenta = new CuentaBancaria(100);

        cuenta.ingresar(50);

        assertEquals(150, cuenta.getSaldo(), 0.001);
    }
}
```

- `@Test` marca el método como prueba. En JUnit 5 la clase y el método **no tienen que ser públicos**.
- `assertEquals(esperado, obtenido, tolerancia)` compara el valor esperado con el real. El **primer** argumento es
  siempre el esperado.
- La **tolerancia** (tercer argumento) es obligatoria al comparar `double`, por los errores de redondeo.

## 4.5. Estructura de una prueba: Arrange, Act, Assert

Un patrón sencillo hace las pruebas legibles:

| Fase        | Qué se hace                                  | En el ejemplo                       |
| ----------- | -------------------------------------------- | ----------------------------------- |
| **Arrange** | Preparar los objetos y datos                 | `new CuentaBancaria(100)`           |
| **Act**     | Ejecutar la acción que se prueba             | `cuenta.ingresar(50)`               |
| **Assert**  | Comprobar el resultado                       | `assertEquals(150, ...)`            |

Buenas prácticas:

- **Una idea por prueba:** si falla, se sabe exactamente qué ha ido mal.
- **Nombres descriptivos:** `retirarMasQueElSaldoLanzaExcepcion` explica qué comprueba sin abrir el código.
- **Pruebas independientes:** ninguna debe depender de lo que haya hecho otra.

## 4.6. Aserciones principales

Las **aserciones** son las comprobaciones. Se importan de `org.junit.jupiter.api.Assertions`.

| Aserción                                  | Comprueba que…                                           |
| ----------------------------------------- | -------------------------------------------------------- |
| `assertEquals(esperado, obtenido)`        | Los dos valores son iguales                              |
| `assertEquals(esperado, obtenido, delta)` | Dos `double` difieren menos que `delta`                  |
| `assertNotEquals(a, b)`                   | Los valores son distintos                                |
| `assertTrue(condición)`                   | La condición es verdadera                                |
| `assertFalse(condición)`                  | La condición es falsa                                    |
| `assertNull(obj)` / `assertNotNull(obj)`  | El objeto es / no es `null`                              |
| `assertArrayEquals(esperado, obtenido)`   | Dos arrays tienen el mismo contenido                     |
| `assertThrows(Tipo.class, () -> ...)`     | El código lanza una excepción del tipo indicado          |
| `assertDoesNotThrow(() -> ...)`           | El código no lanza ninguna excepción                     |
| `assertAll(...)`                          | Se ejecutan varias aserciones y se informa de todos los fallos |
| `fail("mensaje")`                         | Hace fallar la prueba                                    |

### Probar excepciones con `assertThrows`

```java
@Test
void retirarMasQueElSaldoLanzaExcepcion() {
    CuentaBancaria cuenta = new CuentaBancaria(100);

    IllegalStateException e = assertThrows(IllegalStateException.class,
            () -> cuenta.retirar(150));

    assertEquals("Saldo insuficiente", e.getMessage());
}
```

`assertThrows` devuelve la excepción capturada, de modo que se puede comprobar también su mensaje.

## 4.7. Ciclo de vida de una clase de prueba

| Anotación       | Cuándo se ejecuta                                       | Uso típico                                |
| --------------- | ------------------------------------------------------- | ----------------------------------------- |
| `@BeforeAll`    | Una vez, antes de todas las pruebas (método `static`)   | Recursos costosos de crear                |
| `@BeforeEach`   | Antes de **cada** prueba                                | Crear un objeto nuevo y limpio            |
| `@AfterEach`    | Después de **cada** prueba                              | Liberar recursos                          |
| `@AfterAll`     | Una vez, al terminar todas las pruebas (método `static`) | Cerrar recursos compartidos              |

Otras anotaciones útiles:

| Anotación         | Función                                                          |
| ----------------- | ---------------------------------------------------------------- |
| `@DisplayName`    | Da un nombre legible a la prueba en los informes                 |
| `@Disabled`       | Desactiva temporalmente una prueba                               |
| `@Timeout`        | Hace fallar la prueba si tarda más de lo indicado                |

### Ejemplo con `@BeforeEach`

```java
class CuentaBancariaTest {

    private CuentaBancaria cuenta;

    @BeforeEach
    void preparar() {
        cuenta = new CuentaBancaria(100);   // un objeto nuevo antes de cada prueba
    }

    @Test
    @DisplayName("Retirar todo el saldo deja la cuenta a cero")
    void retirarTodoElSaldo() {
        cuenta.retirar(100);
        assertEquals(0, cuenta.getSaldo(), 0.001);
    }

    @Test
    void ingresarCantidadNegativaLanzaExcepcion() {
        assertThrows(IllegalArgumentException.class, () -> cuenta.ingresar(-10));
    }
}
```

Gracias a `@BeforeEach`, cada prueba parte de una cuenta nueva con 100 €, de modo que **las pruebas no se influyen
entre sí**.

## 4.8. Pruebas parametrizadas

Cuando hay que probar muchos valores con el mismo código, se evita copiar y pegar usando una **prueba
parametrizada**:

```java
class EntradaTest {

    @ParameterizedTest
    @CsvSource({
        "0,  INFANTIL",
        "11, INFANTIL",
        "12, ADULTO",
        "64, ADULTO",
        "65, JUBILADO",
        "120, JUBILADO"
    })
    void categoriaSegunLaEdad(int edad, String esperado) {
        assertEquals(esperado, Entrada.categoria(edad));
    }

    @ParameterizedTest
    @ValueSource(ints = {-1, 121})
    void edadesNoValidasLanzanExcepcion(int edad) {
        assertThrows(IllegalArgumentException.class, () -> Entrada.categoria(edad));
    }
}
```

Los imports necesarios son `org.junit.jupiter.params.ParameterizedTest` y las fuentes de datos
`org.junit.jupiter.params.provider.CsvSource` y `ValueSource`. En VS Code cada fila aparece como un resultado
independiente, así que un único valor que falle (por ejemplo, el 12) se identifica de inmediato.

## 4.9. Ejecutar las pruebas en VS Code

### Desde el editor

- Junto a la clase y a cada método `@Test` aparece un **botón verde de reproducción** (*Run Test*) y otro para
  **depurar** (*Debug Test*).
- Un marcador al lado de cada método indica el estado: ✔ verde si pasa, ✘ rojo si falla.

### Desde el Explorador de pruebas (*Testing*)

El icono del **matraz** de la barra lateral abre el **Test Explorer**, que muestra todas las pruebas del proyecto en
forma de árbol (proyecto → paquete → clase → método), con botones para ejecutar todas, solo las fallidas o
depurarlas. Al seleccionar una prueba fallida se ve el mensaje del error con los valores esperado y obtenido.

### Desde la terminal con Maven

```bash
mvn test
```

La salida muestra un resumen como este:

```
[INFO] Tests run: 8, Failures: 1, Errors: 0, Skipped: 0
[ERROR] BUILD FAILURE
```

| Dato          | Significado                                                       |
| ------------- | ----------------------------------------------------------------- |
| **Failures**  | Pruebas cuyas aserciones no se cumplen (resultado incorrecto)     |
| **Errors**    | Pruebas que terminan con una excepción inesperada                 |
| **Skipped**   | Pruebas desactivadas (`@Disabled`)                                |

Los informes detallados se guardan en la carpeta `target/surefire-reports/`.

## 4.10. Depurar una prueba que falla

Cuando una prueba falla, el siguiente paso es **depurar**: ejecutar el código paso a paso para ver por qué se
comporta así.

### Herramientas del depurador de VS Code

| Herramienta                  | Cómo se usa                                                       |
| ---------------------------- | ----------------------------------------------------------------- |
| **Punto de ruptura**         | Clic en el margen izquierdo de una línea (o `F9`)                 |
| **Punto de ruptura condicional** | Clic derecho en el punto → *Edit Breakpoint* → condición (por ejemplo `cantidad == 100`) |
| **Continuar**                | `F5`                                                              |
| **Paso por encima** (*Step Over*) | `F10`: ejecuta la línea sin entrar en los métodos que llame   |
| **Paso adentro** (*Step Into*)    | `F11`: entra en el método de la línea actual                  |
| **Paso afuera** (*Step Out*)      | `Mayús + F11`: sale del método actual                         |
| **Variables**                | Panel que muestra los valores de las variables locales            |
| **Inspección** (*Watch*)     | Permite vigilar una expresión mientras se ejecuta                 |
| **Pila de llamadas** (*Call Stack*) | Muestra qué método llamó a cuál                            |
| **Consola de depuración**    | Permite evaluar expresiones en el punto donde está detenido       |

### Procedimiento recomendado

1. Ejecutar las pruebas y localizar la que falla.
2. Poner un punto de ruptura **al inicio del método** sospechoso.
3. Pulsar *Debug Test* sobre la prueba fallida.
4. Avanzar con `F10` y observar los valores del panel *Variables*.
5. Localizar la línea donde el comportamiento real se aparta del esperado.
6. Corregir el código y **volver a ejecutar todas las pruebas** (regresión).

## 4.11. Medir la cobertura con JaCoCo

**JaCoCo** es la herramienta estándar para medir la cobertura de pruebas en Java. Se añade al `pom.xml` dentro de
`<build><plugins>`:

```xml
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.12</version>
  <executions>
    <execution>
      <goals>
        <goal>prepare-agent</goal>
      </goals>
    </execution>
    <execution>
      <id>report</id>
      <phase>test</phase>
      <goals>
        <goal>report</goal>
      </goals>
    </execution>
  </executions>
</plugin>
```

Al ejecutar `mvn test` se genera un informe en `target/site/jacoco/index.html`, que se abre en el navegador. Muestra,
por paquete y clase:

| Columna                | Significado                                                  |
| ---------------------- | ------------------------------------------------------------ |
| **Instructions**       | Porcentaje de instrucciones de bytecode ejecutadas           |
| **Branches**           | Porcentaje de ramas (resultados de `if`) recorridas          |
| **Lines**              | Porcentaje de líneas de código ejecutadas                    |
| **Methods / Classes**  | Métodos y clases ejecutados al menos una vez                 |

Las líneas se colorean en **verde** (cubiertas), **amarillo** (cubiertas parcialmente, por ejemplo una rama sin
recorrer) y **rojo** (sin ejecutar). En las versiones recientes de VS Code y del *Test Runner for Java* también es
posible lanzar las pruebas con cobertura desde el propio explorador de pruebas.

## 4.12. Dobles de prueba (nociones)

En pruebas unitarias reales, una clase suele depender de otras (una base de datos, un servicio externo). Para probarla
**de forma aislada** se sustituyen esas dependencias por **dobles de prueba**:

| Doble       | Función                                                              |
| ----------- | -------------------------------------------------------------------- |
| **Stub**    | Devuelve respuestas prefijadas                                       |
| **Mock**    | Además, verifica que se le ha llamado de la forma esperada           |
| **Fake**    | Implementación simplificada que funciona (por ejemplo, una base de datos en memoria) |

La biblioteca más usada en Java para crear *mocks* es **Mockito**. No se necesita en las prácticas de este tema, pero
es importante conocer su existencia.

## 4.13. Errores frecuentes al escribir pruebas

| Error                                              | Consecuencia                                          |
| -------------------------------------------------- | ----------------------------------------------------- |
| Comparar `double` sin tolerancia                   | Fallos aleatorios por redondeo                        |
| Poner mal el orden esperado/obtenido               | Mensajes de error engañosos                           |
| Pruebas que dependen unas de otras                 | Fallos que cambian según el orden de ejecución        |
| Varias comprobaciones no relacionadas en un método | No se sabe qué ha fallado exactamente                 |
| Escribir la prueba copiando lo que hace el código  | Se prueba el código, no la especificación             |
| No ejecutar las pruebas con frecuencia             | Los defectos se acumulan y son difíciles de localizar |

## Resumen

| Concepto                | Idea clave                                                                     |
| ----------------------- | ------------------------------------------------------------------------------ |
| **Prueba unitaria**     | Comprueba una unidad de código de forma aislada, rápida y automática           |
| **JUnit 5**             | Framework estándar: `@Test`, aserciones y ciclo de vida con `@BeforeEach`      |
| **Test Runner for Java**| Ejecuta y depura pruebas JUnit desde VS Code                                   |
| **Aserciones**          | `assertEquals`, `assertTrue`, `assertThrows`… comprueban el resultado          |
| **Parametrizadas**      | Un mismo test con muchos datos (`@CsvSource`, `@ValueSource`)                  |
| **Depuración**          | Puntos de ruptura, `F10`/`F11` y panel de variables para localizar la causa    |
| **JaCoCo**              | Mide la cobertura de líneas y ramas de las pruebas                             |
