# 1. Planificación de pruebas

Probar un programa sin un plan es como revisar una casa abriendo puertas al azar: se encontrará algo, pero nadie sabrá
qué partes quedaron sin mirar. La **planificación de pruebas** consiste en decidir de antemano **qué se va a probar,
cómo, con qué recursos y cuándo se dará la prueba por terminada**.

En este apartado se estudia la terminología básica, los niveles de prueba, los principios que guían cualquier
estrategia de pruebas y los documentos que se generan: el plan de pruebas, los casos de prueba y los informes de
incidencias.

## 1.1. ¿Qué son las pruebas de software?

Las **pruebas de software** son el conjunto de actividades que se realizan para **evaluar si un programa cumple sus
requisitos y para descubrir defectos antes de que lleguen al usuario**.

Los objetivos principales son:

- Detectar defectos lo antes posible.
- Comprobar que el programa hace lo que debe hacer.
- Comprobar que no hace lo que no debe hacer.
- Generar confianza en la calidad del producto.
- Facilitar los cambios futuros sin miedo a romper algo.

### Error, defecto y fallo

Aunque en el lenguaje cotidiano se usan como sinónimos, en pruebas tienen significados distintos:

| Término      | Significado                                                              | Ejemplo                                                   |
| ------------ | ------------------------------------------------------------------------ | --------------------------------------------------------- |
| **Error**    | Equivocación cometida por una persona                                    | El programador escribe `>=` en lugar de `>`               |
| **Defecto**  | Anomalía en el código o en un documento, consecuencia de un error        | La línea `if (cantidad >= saldo)` del código               |
| **Fallo**    | Comportamiento incorrecto observable cuando se ejecuta el código defectuoso | Al retirar todo el saldo, el programa lanza una excepción |

La cadena es siempre la misma: **un error humano introduce un defecto, y el defecto, al ejecutarse, puede producir un
fallo**. No todos los defectos producen fallos en todas las ejecuciones.

### Verificación y validación

| Concepto         | Pregunta que responde                          | Ejemplo                                              |
| ---------------- | ---------------------------------------------- | ---------------------------------------------------- |
| **Verificación** | ¿Estamos construyendo el producto correctamente? | Revisar que el código sigue el diseño                |
| **Validación**   | ¿Estamos construyendo el producto correcto?    | Comprobar con el cliente que resuelve su necesidad   |

## 1.2. Principios de las pruebas

Estos siete principios, aceptados en la ingeniería de software, orientan cualquier estrategia de pruebas:

1. **Las pruebas muestran la presencia de defectos, no su ausencia.** Que no se encuentre ningún fallo no demuestra
   que el programa sea perfecto.
2. **Las pruebas exhaustivas son imposibles.** Una función con dos números enteros ya tiene miles de millones de
   combinaciones. Hay que elegir bien los casos.
3. **Probar pronto ahorra tiempo y dinero.** Un defecto encontrado en el diseño cuesta mucho menos que uno encontrado
   por el cliente.
4. **Los defectos se agrupan.** Una pequeña parte del código suele concentrar la mayoría de los fallos.
5. **Paradoja del pesticida.** Si se repiten siempre las mismas pruebas, dejarán de encontrar defectos nuevos; hay que
   revisarlas y ampliarlas.
6. **Las pruebas dependen del contexto.** No se prueba igual una aplicación bancaria que un videojuego.
7. **Falacia de la ausencia de errores.** Un software sin defectos conocidos no es útil si no cubre las necesidades
   del usuario.

## 1.3. Niveles de prueba

Las pruebas se realizan en distintos momentos y con distinto alcance. Los cuatro niveles clásicos son:

| Nivel                     | Qué se prueba                                         | Quién suele hacerlo        | Ejemplo                                           |
| ------------------------- | ----------------------------------------------------- | -------------------------- | ------------------------------------------------- |
| **Pruebas unitarias**     | Una clase o método de forma aislada                   | El programador             | Probar el método `retirar` de `CuentaBancaria`    |
| **Pruebas de integración**| La comunicación entre varios componentes              | Programadores / equipo QA  | Comprobar que la cuenta y el servicio de transferencias funcionan juntos |
| **Pruebas de sistema**    | El programa completo en un entorno parecido al real   | Equipo de pruebas          | Probar la aplicación entera desde la interfaz     |
| **Pruebas de aceptación** | Si el sistema cumple lo que el cliente necesita       | Cliente o usuarios         | El cliente valida el sistema antes de recibirlo   |

### La pirámide de pruebas

Una estrategia equilibrada tiene **muchas pruebas unitarias** (rápidas y baratas), **algunas de integración** y
**pocas pruebas de sistema** (lentas y costosas):

```
          /\
         /  \      Pruebas de sistema / aceptación (pocas, lentas)
        /----\
       /      \    Pruebas de integración (algunas)
      /--------\
     /          \  Pruebas unitarias (muchas, rápidas)
    /------------\
```

## 1.4. El plan de pruebas

El **plan de pruebas** es el documento que describe cómo se van a realizar las pruebas de un proyecto. Un plan
sencillo incluye:

| Apartado                        | Qué contiene                                                        |
| ------------------------------- | ------------------------------------------------------------------- |
| **Objetivo**                    | Qué se quiere conseguir con las pruebas                             |
| **Alcance**                     | Qué se prueba y qué queda fuera                                     |
| **Estrategia**                  | Tipos y niveles de prueba que se aplicarán                          |
| **Recursos**                    | Herramientas (VS Code, JUnit, Maven), entornos y personas           |
| **Criterios de entrada**        | Qué debe cumplirse para empezar a probar (el código compila)        |
| **Criterios de salida**         | Cuándo se dan las pruebas por terminadas (todos los casos pasan, cobertura mínima) |
| **Calendario**                  | Plazos de las actividades de prueba                                 |
| **Riesgos**                     | Qué puede dificultar las pruebas                                    |

### Ejemplo reducido de plan de pruebas

| Apartado             | Contenido                                                                          |
| -------------------- | ---------------------------------------------------------------------------------- |
| Objetivo             | Verificar que la clase `CuentaBancaria` cumple sus especificaciones                |
| Alcance              | Métodos `ingresar`, `retirar` y `getSaldo`; no se prueba la interfaz               |
| Estrategia           | Pruebas unitarias de caja negra y blanca con JUnit 5                               |
| Recursos             | VS Code, JDK, Maven, Test Runner for Java                                          |
| Criterio de entrada  | El proyecto compila sin errores                                                    |
| Criterio de salida   | Todos los casos superados y cobertura de líneas igual o superior al 90%            |

## 1.5. Casos de prueba

Un **caso de prueba** es la descripción de **una situación concreta que se va a probar**: qué datos se introducen y
qué resultado se espera. Un buen caso de prueba debe ser **claro, repetible e independiente**.

### Estructura de un caso de prueba

| Campo                     | Descripción                                             |
| ------------------------- | ------------------------------------------------------- |
| **ID**                    | Identificador único (CP-01, CP-02…)                     |
| **Descripción**           | Qué se quiere comprobar                                 |
| **Precondiciones**        | Estado inicial necesario                                |
| **Datos de entrada**      | Valores con los que se prueba                           |
| **Resultado esperado**    | Lo que debe ocurrir según la especificación             |
| **Resultado obtenido**    | Lo que ocurre realmente al ejecutar                     |
| **Estado**                | Correcto / Fallo                                        |

### Ejemplo

| ID    | Descripción                       | Precondición         | Entrada            | Resultado esperado           | Obtenido | Estado |
| ----- | --------------------------------- | -------------------- | ------------------ | ---------------------------- | -------- | ------ |
| CP-01 | Ingresar una cantidad positiva    | Cuenta con 100 €     | `ingresar(50)`     | Saldo = 150                  | 150      | Correcto |
| CP-02 | Ingresar una cantidad negativa    | Cuenta con 100 €     | `ingresar(-10)`    | Lanza `IllegalArgumentException` | Lanza | Correcto |

> **Importante:** el resultado esperado se decide **a partir de la especificación**, nunca mirando lo que hace el
> código. Si no, se estaría comprobando que el código hace lo que hace, no lo que debe.

## 1.6. Ciclo de vida de las pruebas

| Fase                      | Actividad                                                         |
| ------------------------- | ----------------------------------------------------------------- |
| **1. Planificación**      | Se redacta el plan de pruebas                                     |
| **2. Diseño**             | Se escriben los casos de prueba                                   |
| **3. Preparación**        | Se prepara el entorno y los datos                                 |
| **4. Ejecución**          | Se ejecutan los casos y se registran los resultados               |
| **5. Informe**            | Se registran los defectos y se resumen los resultados             |
| **6. Cierre**             | Se comprueba si se cumplen los criterios de salida                |

## 1.7. Informe de incidencias

Cuando una prueba falla, el defecto debe documentarse de forma que otra persona pueda **reproducirlo y corregirlo**.

| Campo                    | Ejemplo                                                              |
| ------------------------ | -------------------------------------------------------------------- |
| **ID de incidencia**     | INC-001                                                              |
| **Título**               | No se puede retirar todo el saldo de la cuenta                       |
| **Pasos para reproducir**| 1. Crear cuenta con 100 €. 2. Llamar a `retirar(100)`                |
| **Resultado esperado**   | Saldo final = 0                                                      |
| **Resultado obtenido**   | Se lanza `IllegalStateException: Saldo insuficiente`                 |
| **Gravedad**             | Alta                                                                 |
| **Estado**               | Abierta                                                              |

## 1.8. Pruebas manuales y automáticas

| Aspecto            | Pruebas manuales                          | Pruebas automáticas                           |
| ------------------ | ----------------------------------------- | --------------------------------------------- |
| Ejecución          | Una persona ejecuta y observa             | Un programa ejecuta y comprueba               |
| Coste inicial      | Bajo                                      | Mayor (hay que escribir el código de prueba)  |
| Coste de repetir   | Alto                                      | Casi nulo                                     |
| Fiabilidad         | Depende del cuidado de la persona         | Siempre hace las mismas comprobaciones        |
| Ideal para         | Pruebas exploratorias y de usabilidad     | Pruebas unitarias y de regresión              |

En este tema se empezará con pruebas manuales para entender el proceso y se terminará automatizándolas con JUnit.

## Resumen

| Concepto                | Idea clave                                                              |
| ----------------------- | ----------------------------------------------------------------------- |
| **Error / defecto / fallo** | El error humano origina un defecto; al ejecutarlo puede dar un fallo |
| **Principios**          | Se prueba para encontrar defectos, pero nunca se demuestra su ausencia  |
| **Niveles**             | Unitarias, integración, sistema y aceptación                            |
| **Plan de pruebas**     | Documento con objetivo, alcance, estrategia, recursos y criterios       |
| **Caso de prueba**      | Entrada concreta, resultado esperado y resultado obtenido               |
| **Incidencia**          | Informe reproducible de un defecto encontrado                           |
