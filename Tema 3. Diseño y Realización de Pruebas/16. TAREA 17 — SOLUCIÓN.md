### Código final

```java
package com.ejemplo.facturacion;

public class Factura {

    private static final double IVA = 0.21;
    private static final double DESCUENTO_VIP = 0.15;
    private static final double DESCUENTO_NORMAL = 0.05;
    private static final double DESCUENTO_NUEVO = 0.0;

    public double calcularTotal(double[] precios, int[] cantidades, String tipoCliente) {
        double subtotal = calcularSubtotal(precios, cantidades);
        double conDescuento = aplicarDescuento(subtotal, tipoCliente);
        return aplicarIva(conDescuento);
    }

    private double calcularSubtotal(double[] precios, int[] cantidades) {
        double subtotal = 0;
        for (int i = 0; i < precios.length; i++) {
            subtotal += precios[i] * cantidades[i];
        }
        return subtotal;
    }

    private double aplicarDescuento(double importe, String tipoCliente) {
        return importe - importe * obtenerPorcentajeDescuento(tipoCliente);
    }

    private double obtenerPorcentajeDescuento(String tipoCliente) {
        switch (tipoCliente) {
            case "VIP":
                return DESCUENTO_VIP;
            case "NORMAL":
                return DESCUENTO_NORMAL;
            case "NUEVO":
                return DESCUENTO_NUEVO;
            default:
                return 0;
        }
    }

    private double aplicarIva(double importe) {
        return importe + importe * IVA;
    }
}
```

El comportamiento es **idéntico**: incluso con `null` como tipo de cliente se lanza `NullPointerException`, igual que
en el código original (`t.equals(...)`).

**Criterios de corrección:** al menos cuatro refactorizaciones con las herramientas de VS Code (0,80) · pruebas
ejecutadas tras cada paso (0,70) · tabla clara con técnica, forma de aplicarla y resultado (0,50) · código final
correcto y con el mismo comportamiento (0,50).

## 3. Nueva funcionalidad con TDD (1,50 puntos)

**Red.** Se añade primero la prueba (con el código todavía sin `"EMPRESA"`):

```java
@Test
void clienteEmpresaTiene10PorCientoDeDescuento() {
    // 40 - 4 = 36; 36 + 36 * 0.21 = 43.56
    assertEquals(43.56, factura.calcularTotal(precios, cantidades, "EMPRESA"), 0.001);
}
```

Al ejecutarla **falla**: como `"EMPRESA"` es un tipo desconocido, no se aplica descuento y el resultado es 48,4.

```
expected: <43.56> but was: <48.4>
```

**Green.** Se escribe el código mínimo para que pase:

```java
private static final double DESCUENTO_EMPRESA = 0.10;
...
case "EMPRESA":
    return DESCUENTO_EMPRESA;
```

Ahora las **seis** pruebas están en verde (`Tests run: 6, Failures: 0`).

**Refactor.** Con todo en verde se revisa el código. La constante ya tiene nombre explícito y el `switch` mantiene un
`case` por tipo, por lo que no hace falta ningún cambio más. Se vuelven a ejecutar las pruebas y siguen en verde.

**Criterios de corrección:** prueba escrita primero y captura en rojo (0,50) · implementación mínima y captura en
verde (0,50) · fase de refactorización considerada y pruebas finales en verde (0,50).

## 4. Las pruebas detectan un error de refactorización (1,00 punto)

Error introducido al extraer la constante:

```java
private static final double DESCUENTO_NORMAL = 0.5;   // debería ser 0.05
```

Al ejecutar las pruebas **falla una sola**: `clienteNormalTiene5PorCientoDeDescuento`.

```
expected: <45.98> but was: <24.2>
```

Las demás pasan porque no usan el tipo `NORMAL`. Tras restaurar `0.05`, vuelven a pasar las seis.

**Explicación:** este es el valor de la red de seguridad. Un simple cambio de un cero habría pasado inadvertido
visualmente en la revisión del código, pero la prueba lo detectó al instante y señaló con precisión el caso afectado.

**Criterios de corrección:** error introducido y prueba fallida identificada con su mensaje (0,50) · error deshecho
y todo en verde (0,25) · explicación (0,25).

## 5. Malos olores del código original (1,50 puntos)

| Mal olor                                               | Dónde aparece                                   | Técnica y justificación                                                  |
| ------------------------------------------------------ | ----------------------------------------------- | ------------------------------------------------------------------------ |
| **Nombres poco claros**                                | `p`, `c`, `t`, `tt`                             | **Renombrar** (`F2`): el lector entiende qué representa cada dato        |
| **Números mágicos**                                    | `0.15`, `0.05`, `0.0`, `0.21`                   | **Extraer a constante**: el valor tiene nombre y se cambia en un solo sitio |
| **Método que hace demasiadas cosas**                   | `calcularTotal` calcula subtotal, descuento e IVA | **Extraer método**: cada responsabilidad tiene su método con nombre      |
| **Cadena de condicionales repetitiva**                 | `if / else if` con `tt = tt - tt * X` repetido  | **Extraer método** y **simplificar condicional** con `switch`            |
| **Variable reutilizada con significados distintos**    | `tt` es subtotal, importe con descuento y total | **Extraer variables locales** con nombre propio (`subtotal`, `conDescuento`) |
| **Código redundante**                                  | `tt - tt * 0.0` no tiene efecto                 | Mantenerlo como constante explícita o **eliminarlo** si se decide        |

## 6. Pruebas, Red-Green-Refactor y tipos de cambio (1,50 puntos)

**Papel de las pruebas al refactorizar:** actúan como **red de seguridad**. La refactorización no debe cambiar el
comportamiento, y las pruebas son lo que permite comprobarlo de forma rápida y automática después de cada cambio
pequeño. Sin ellas, cualquier modificación de la estructura es un riesgo que nadie puede medir.

**Ciclo Red-Green-Refactor:**

1. **Red:** escribir una prueba que falla porque la funcionalidad no existe.
2. **Green:** escribir el código mínimo para que la prueba pase.
3. **Refactor:** mejorar el código con todas las pruebas en verde.

| Actividad                   | ¿Cambia el comportamiento? | Ejemplo en esta práctica                                  |
| --------------------------- | -------------------------- | --------------------------------------------------------- |
| **Refactorizar**            | No                         | Extraer `calcularSubtotal` o renombrar `tt` a `total`     |
| **Corregir un defecto**     | Sí, para ajustarlo a la especificación | Cambiar `>=` por `>` en `retirar`              |
| **Añadir funcionalidad**    | Sí, añade comportamiento nuevo | Añadir el tipo de cliente `EMPRESA`                   |

Conviene **no mezclarlas** en un mismo paso, para saber siempre cuál de ellas ha provocado un problema.

## Conclusión

Refactorizar con pruebas permite mejorar un código poco legible sin miedo a romperlo: primero se fija su comportamiento,
después se transforma paso a paso con la red de seguridad en verde y, por último, se amplía de forma ordenada con TDD.
El error deliberado del apartado 4 demostró que esa red funciona.
